## Why

The archived onboarding change (`2026-08-06-onboarding-enable-banking`) delivered Enable Banking application registration (control-plane `POST /api/register`) and the email-link authentication flow, but stopped short of linking a PSU's bank account and creating a usable AIS session. Without these, the registered application has no whitelisted accounts and no session to read account data from. This change closes that gap by implementing the two-step PSU authorization flow: (1) **account linking** via the control-plane `POST /api/link_accounts` (whitelists the PSU's account on the application) and (2) **session authorization** via the data-plane `POST /auth` → bank SCA → `POST /sessions` (creates an AIS session for reading account data).

The dashboard is **not modified** by this change. Completing onboarding (including linking + auth) simply forwards to the existing dashboard. What happens there is outside the scope of this change — the dashboard content has not been specified yet and will be refactored in a follow-up.

## What Changes

- **Persist the Firebase refreshToken**: The onboarding completion endpoint now persists `enable_banking_refresh_token` alongside `application_id` and `private_key`. The email-link callback captures the `refreshToken` from the `emailLinkSignin` response. The refresh token is validated at login (the login step calls `refreshIdToken` to confirm it works). No fallback re-authentication flow is specified — if the refresh token is invalid at login, the user must re-onboard.

- **Add idToken refresh capability**: The control-plane client gains a `refreshIdToken(refreshToken)` method that calls the Google Identity Toolkit token-refresh endpoint (`securetoken.googleapis.com/v1/token` with `grant_type=refresh_token`). The server calls this proactively before every control-plane request (specifically `link_accounts`) to obtain a fresh idToken. Since a fresh idToken is always used, 401 responses are not expected and no retry pattern is needed. `refreshIdToken` owns the full token lifecycle: on success it persists the (possibly rotated) refresh token to `system_config`; on failure (invalid/expired/revoked) it clears the token so the next onboarding-state check routes the user to re-login (the user re-does only the email-link login step — `application_id` and `private_key` remain valid). Transient errors (network, 5xx) do NOT clear the token.

- **Add data-plane ASPSP listing**: The data-plane client gains a `getAspsps()` method that calls `GET /aspsps` (RS256 JWT auth — no Firebase token needed). The server exposes `GET /api/aspsps` (session-authenticated) which fetches **all** banks without server-side filtering — the SPA filters client-side.

- **Add control-plane account linking**: The control-plane client gains a `linkAccounts(...)` method that calls `POST /api/link_accounts` (Firebase idToken auth). The `redirect_url` parameter is a **fixed constant** `https://enablebanking.com/api/auth_redirect` (Enable Banking's own control-panel callback — external redirect URLs do not work), shipped as a code constant in the client. The server exposes `POST /api/link-accounts` (session-authenticated).

- **Add data-plane auth + session creation**: The data-plane client gains `startAuth(...)` and `authorizeSession(code)` methods. The server exposes `POST /api/auth` (session-authenticated). The existing `GET /enable-banking-callback` route is extended to handle auth returns (`code` + `state`): since the auth redirect happens in the **same browser tab**, the session cookie is expected; on missing cookie the route 302 redirects to the BankTeller login page (username/password, not the Enable Banking email-link flow) and discards the single-use `code`. On auth failure (invalid code, bank denied, technical error), the route stores the error reason as `auth_error` in the **BankTeller user session** (ephemeral, tied to the session cookie — not `system_config` or a database) so the SPA can display it on the LinkingProgress screen with a "Continue to authorization" retry button.

- **Add onboarding-state resume flow**: The server exposes `GET /api/onboarding/state` (session-authenticated) which returns a structured response with **routing flags** and **display-only fields**: `{ "requires_relogin": bool, "linking_completed": bool, "auth_completed": bool, "auth_error": string|null, "selected_bank": object|null }`. The SPA determines routing exclusively from the flags — it never parses `auth_error` string values for control flow (per design decision D10). `requires_relogin` is the sole re-login signal (true iff `enable_banking_refresh_token` is missing from `system_config`, cleared by `refreshIdToken`); `linking_completed`/`auth_completed` indicate onboarding progress; `auth_error` is display-only (the error message to show, or null); `selected_bank` carries `{ "aspsp_name", "aspsp_country", "psu_type" }` from the prior `POST /api/link-accounts` call so the SPA can pass it to `POST /api/auth` in the resume flow (after a reload, viewmodel state is gone — `POST /api/auth` requires these in the request body). The SPA calls this on load to route: `requires_relogin=true` → re-login; `(false, false, false)` → fresh start (ActivationGuide); `(false, true, false)` → LinkingProgress with "Continue to authorization" button (resume after new tab or cancelled auth); `(false, true, false)` + `auth_error!=null` → LinkingProgress with error message + retry button (resume after auth failure); `(false, true, true)` → dashboard. The `auth_error` is **ephemeral session state** (distinct from `enable_banking_refresh_token`, which lives in `system_config` because it must survive logout) and is cleared at two points: (1) when `POST /api/auth` is called — the user has acknowledged the error and is starting a fresh attempt, so the error is cleared at the start of the request (preventing a stale error from appearing in a subsequently opened tab); (2) when the auth callback succeeds (belt-and-suspenders). The error is shown exactly once: on the LinkingProgress screen after a failed callback, and it disappears the moment the user clicks "Continue to authorization".

- **Add link-completion check**: The server exposes `GET /api/onboarding/link-status` (session-authenticated) which checks `GET /application` for a `psu_id_hash` match in `whitelisted_accounts`. This is a **single check on demand** (triggered by a user-clicked button), not background polling.

- **Extend SPA onboarding gate**: After `ActivationGuide` (updated to explain the two-step process), add a `BankSelection` step (searchable bank list, client-side filtering), a `LinkingProgress` step (opens bank SCA in a new tab, shows an "I've completed linking, authorize now" button — no background polling), and an `AuthProgress` step (redirects current tab to bank SCA, handles callback). On success, the SPA forwards to the existing dashboard (unchanged). The UI design was specified by @designer and is documented in `design.md` → "UI Design".

## Impact

- **New spec capabilities**: `enable-banking-client` (data-plane ASPSP listing, auth initiation, session authorization; control-plane account linking, idToken refresh with token-lifecycle ownership, refreshToken parsing), `onboarding` (bank listing, account linking, auth initiation, link-completion check, onboarding-state resume flow, SPA steps).
- **Modified spec capabilities**: `onboarding` (email-link callback now also handles auth returns — with 302-to-login on missing cookie and error-reason storage on failure; completion endpoint persists refreshToken; reset endpoint blanks refreshToken; onboarding detection routes through new steps).
- **Spec capabilities NOT modified**: Dashboard — untouched, out of scope.
