# Proposal

## Why

The `wcag-color-conformance` change (archived 2026-11-21) established the WCAG 2.2 AA conformance frame and closed the color-side criteria, but the semantic/interaction side remains unaddressed: a live spike (2026-11-21/23, dev server + browser probes) found that with the Compose 1.11.1 DOM-overlay bridge working — real geometry, verbatim `contentDescription`→`aria-label` projection, functioning click listeners on exposed nodes — the app still *declares* almost nothing: icon-only controls are unlabeled, hand-rolled controls (tab bar, nav rows, dense controls) expose no roles or states, no headings exist in the tree, async status changes are silent, and text fields expose no accessible names. Source-level research (compose-multiplatform-core v1.11.1 vs jb-main, issue trail #3035/#3226/#3381/#3428/#3235, CMP-10172/CMP-10413/CMP-10226) additionally established precisely which semantics the framework projects at each version and that keyboard traversal/focus exposure is a framework gap, not an app defect. The user's primary goal for this capability (explicit ruling): a *framework* that keeps the app WCAG-compatible through future development — automatically via tests where possible, otherwise via spec-enforced declaration duties — rather than a one-time conformance cleanup. A second, evidence-backed beneficiary: agent-controllability (the original motivation of this whole thread) — the spike proved that exposing semantics makes the app both readable and *drivable* (overlay-node click executed the real theme-toggle cycle and persisted state), without needing keyboard focus.

## What Changes

- **Compose Multiplatform upgrade to ≥1.12** (user ruling: regular dependency updates): delivers the a11y-container geometry fix (CMP-10172/#3035/#3226), `aria-disabled`/`aria-selected`/`aria-readonly` mappings (#3381), `liveRegion → aria-live` (#3428), and slider tab stops. Landed as the change's first implementation task so every later task builds on the richer bridge.
- **Semantic primitive layer** in `ui/components/` — reusable components that carry their WCAG semantics by construction (the enforcement core): a semantic icon-action wrapper (mandatory `contentDescription`/`onClickLabel`), a `StatusText` with `liveRegion` for async announcements (sync line, busy states, waiting indicators), heading semantics for screen titles, tab/navigation-row semantics with `Role.Tab`/`Sel`, and a field wrapper that merges the accessible name onto text inputs, and collection semantics on list-bearing containers (the dashboard account cards, connection accounts lists). The field wrapper exists because the spike found the M3 textboxes expose `role="textbox"` but no name — the label renders as a separate, unassociated node. Any screen built from these primitives is structurally conformant by construction (the per-surface async-announcement declaration remains, per the accessibility duty).
- **Declaration migration** across all existing screens (login, onboarding wizard, dashboard, settings, callback, legal): label every icon-only control, role/state every hand-rolled control, heading every screen title, liveRegion every async status, merge field labels — with a component inventory as the first task so the migration is checklist-driven.
- **Semantics unit tests** (the automatic half of the enforcement framework): JVM tests in the `:app:web` test-only target (the home established by `wcag-color-conformance`) asserting the primitive layer's semantics contracts — every primitive's role/label/state/liveRegion declarations verifiable on JVM, new primitives added to the set. Extends the contrast-test culture from color to semantics.
- **Declaration duty in specs** (the precondition half): a new requirement in the `accessibility` capability — every new UI surface's change MUST declare its semantic primitive usage and its async-announcement behavior, reviewed like the other accessibility rulings.
- **WCAG verdict records** established per the verdict policy from `wcag-color-conformance` (all recorded in this change's design notes): 2.1.1 (keyboard) and 2.4.3 (focus order) recorded as *exempted (framework-blocked)* with the YouTrack trail as evidence (no tabindex wiring, no focus sync in 1.11.1, and even jb-main wires only sliders); 1.1.1/1.3.1/4.1.2 (labels, structure, name-role-value) recorded as *conforms via the primitive layer*; 2.4.6 (headings and labels) — *conforms* via heading semantics + field names; 4.1.3 (status messages) as *conforms via liveRegion declarations* (post-1.12); 2.4.7 (focus visible) record-applicable as *exempted with reasoning* (Compose focus indication draws on the canvas; DOM-visible focus does not exist for canvas-internal elements).
- **Agent-controllability as an explicit beneficiary**: documented alongside the WCAG work — the overlay read + node-click mechanism verified by the spike; read/write capability asserted as an optional manual-verification task (drive the theme toggle and tab bar through the overlay).
- **Explicitly deferred**: keyboard/focus remediation (framework-blocked — tracked as upstream; the record lists the YouTrack issues to monitor), browser-zoom re-verification for 1.12 (covered by the prior change's verdict unless the upgrade regresses it), and any Compose-HTML migration consideration (research record: the accessibility bridge is versioned in `webMain` shared source — JS and wasmJs targets project identically; a target switch would change nothing a11y-wise).

## Capabilities

### New Capabilities

- `semantic-ui-primitives`: The reusable component layer that carries WCAG semantics by construction — semantic icon actions, status text with liveRegion, headings, tab/navigation semantics, field-label merging — plus the JVM test contracts that lock each primitive's semantics. Every screen composed from the primitives inherits STRUCTURAL conformance (the per-surface async-announcement declaration remains per the accessibility duty); the primitives are the enforcement mechanism for future development.

### Modified Capabilities

- `accessibility`: The conformance frame gains the semantics side — the declaration duty for new UI surfaces, the name/role/value and status-announcement requirements the primitives implement, and the framework-blocked verdicts (keyboard, focus order, focus-visible) with their upstream evidence trail.
- `design-system-theme`: The shared-component requirements (`ThemeToggle`, tab bar component) gain their semantic contracts — the declarations (labels, roles, states) each component MUST carry wherever it renders, so the two hand-rolled chrome components are conformant by spec, not per-usage.

## Impact

- **Code**: `app/web/build.gradle.kts` (jvmTest filter amendment), `ui/components/` (new primitive layer + existing components gaining semantics), all screen files (`LoginScreen.kt`, `OnboardingScreen.kt`, `DashboardScreen.kt`, `SettingsScreen.kt`, `CallbackScreen.kt`, legal screens) for declaration migration.
- **Tests**: new `SemanticsContractTest.kt` in `app/web/src/commonTest/` (JVM, semantics assertions over the primitive layer); the `jvmTest` filter in `app/web/build.gradle.kts` extended to include it (the existing include-pattern filter would otherwise silently exclude the new test — the enforcement requirement depends on the filter amendment).
- **Dependencies**: Compose Multiplatform 1.11.1 → ≥1.12 in `gradle/libs.versions.toml` (the version catalog, not the module build file; may pull Kotlin/plugin alignment; the version bump task includes the upgrade verification: full `jvmTest` + wasmJs compile + container dev-boot smoke).
- **Docs**: `DESIGN-LANGUAGE.md` gains the semantics-declaration rules (the primitives' contracts are design-language material, like the color rules); the WCAG verdict ledger for this change lives in the change's design notes (per the conformance-target requirement: verdicts live in the design record of the change that established them — never edited into the main spec outside the delta flow).
- **No API, database, or server changes.** No user-visible visual change intended — semantics are non-visual; the only perceptible difference for sighted users is none (for screen-reader users, the app becomes navigable; for agents, drivable).
