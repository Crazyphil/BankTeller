## 2. Server — route resolver

- [ ] 2.1 Implement the pure server-side route resolver (new file, e.g. `server/src/main/kotlin/it/kapfer/bankteller/onboarding/OnboardingRouteResolver.kt`): consumes (application state per `eb-application-status`, whitelist derivation, `eb_sessions`/`hasAnySession()`, session stage + bank triple) and returns the resolved route (`email_entry` | `registration_review` | `activation_guide` | `linking_progress` | `auth_progress` | `bank_selection` | `dashboard`). Ladder per design D3, activation-first order: `requires_relogin` (refresh token absent) OR partial EB config (refresh token present but application id blank — reachable only by manual DB edit; exact parity with the current gate) → `email_entry`; `deleted` → `registration_review`; `inactiveNeverLinked` → `activation_guide` unless a stored stage is honored; stage branch (consumed only when `auth_completed == false`; `auth_progress` requires `linking_completed == true`; `linking_progress`/`auth_progress` with a missing/blank bank triple treated as no stage; `bank_selection` always consumable); `eb_sessions` row → `dashboard`; `inactiveButLinked` best-effort continuation; `auth_failed` → `auth_progress`; whitelist non-empty → `bank_selection`; else → `bank_selection`. Pure function — no I/O, all inputs passed in, hermetically testable
- [ ] 2.2 Wire the resolver into `GET /api/onboarding/state` (AccountLinkingRoutes.kt): report `route` (always present), `app_state`, and `pending_action` (both from the cached `OnboardingService.getStatus()` derivation the resolver consumes — the 30 s status cache; `pending_action` preserves the `eb-application-status` capability's non-blocking pending-action note, which the gate previously obtained from `GET /api/onboarding/status`) alongside the existing flags
