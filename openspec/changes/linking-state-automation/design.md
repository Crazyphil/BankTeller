## Context

The LinkingProgress onboarding step currently requires the user to click "I've completed linking" at the right moment. The external Enable Banking (EB) linking process runs in a separate tab (EB control panel → consent screen → bank SCA), and the user has no signal for when it has actually finished — they click too early (still on the bank's success page) or too late (after logging into the EB control panel, which is not required).

Investigation (live probes against a real linking session) established:

- EB's AIS web app (`tilisy.enablebanking.com/ais/`) polls `GET /ais/get_session_status` against itself, authenticated solely by a `sessionid` cookie. The sessionid equals the `?sessionid=` query parameter of the `authorization_url` that `POST /api/link-accounts` already returns (verified by the user against a live session).
- The minimal request works server-side: cookie-only GET, no query params, no `Referer`, no browser `User-Agent` (verified via curl from the server's egress). The `current_uri` parameter is cosmetic.
- Error contract: HTTP 400 with `{"detail":{"code":"INVALID_SESSION"}}` for an invalid/expired sessionid; 400 `Missing session id` without the cookie. Clean and distinguishable.
- Observed status values (live probes): `NotReady`, `WaitingUserDataSharingConsent`, `WaitingUserUIAuth`, `BankUI`, `AuthDone`, `Cancelled`.
- Reverse-engineering of the Tilisy AIS frontend bundle (the compiled Vue app that calls `get_session_status`) closed the vocabulary question: the AIS component dispatches statuses via **dynamic method lookup** — `this["handle" + status]`, with an explicit error for unknown values — so the status vocabulary is exactly the set of `handle*` methods. Full AIS flow vocabulary: `NotReady`, `AuthStarted`, `WaitingUserUIAuth`, `WaitingUserDecoupledAuth`, `BankUI`, `ReturnedFromBank`, `WaitingUserDataSharingConsent`, plus EB-internal UI steps (`Authentication`, `DataSharingConsent`, `AccountList`, `AccountSelection`) and exactly **three terminal statuses**: `AuthDone`, `Cancelled`, and `Invalid` (EB's own handler renders "Unable to authenticate" — a server-side failure where the user did nothing wrong). EB's own frontend polls at 500ms–1s, and the GET is passive — all side effects live in EB's own handlers, so BankTeller's read-only poll triggers nothing at EB's side.
- The endpoint is undocumented — but so is the entire EB control-plane API (`/api/link_accounts`, `/api/aspsps`, `/api/applications`) the codebase already depends on. Same class of dependency: internal to EB's own products, load-bearing for them.
- EB is visibly migrating hosts (`tilisy.enablebanking.com` → `auth.enablebanking.com` in current docs; the `AuthDone` response's `redirect_url` still points at the legacy `api.tilisy.com`).
- Live end-to-end testing (post-design) confirmed the ordering race the original D5 hedged against: the tilisy status flips to `AuthDone` strictly before the whitelist (`getApplication`) reflects the new link — the EB callback processing the redirect lands (milli-)seconds later. The whitelist is the lagging signal; a confirm fired at the first `AuthDone` observation loses the race in the common case. (Whether the EB callback or Tilisy's own backend updates the whitelist is unobservable from BankTeller and irrelevant — both produce the same lag, handled identically by retry.)

Relevant existing architecture (stable specs, post `persist-onboarding-view-position` archive):

- `POST /api/link-accounts` writes the `linking_progress` view-position stage (bank triple) to the session cookie; the route resolver restores the LinkingProgress step on cold boot within a session.
- `GET /api/onboarding/link-status` performs a single whitelist check (forceRefresh, bypasses the 60s/10s TTL caches) — the authoritative "is the account linked" signal.
- The original "No background polling" design decision (archive/2026-08-24) was specifically about poll-bombing the whitelist check (each check = Firebase idToken refresh + `getApplication`). This change does not poll that path; it polls a different, lighter endpoint with no auth dance, and keeps the whitelist check single-shot.

## Goals / Non-Goals

**Goals:**

- Remove the timing burden from the user: the LinkingProgress step advances automatically once linking is confirmed.
- React to exactly three terminal states: done (`AuthDone`), cancelled (`Cancelled`), and failed (`Invalid`). Everything else — known intermediates or unknown values — is `waiting`.
- Degrade safely: any polling failure (endpoint change, `INVALID_SESSION`, network) silently falls back to today's static manual-button screen. Never worse than status quo.
- Keep the "Re-open linking page" affordance available at all times (accidental tab-close recovery).
- Mirror the email-link waiting experience: indefinite, calm, no poll cap.

**Non-Goals:**

- Automating the authorization step — auth already has the code-callback-driven flow and a pleasant UX; there is no BankTeller tab left to poll during bank SCA anyway.
- Interpreting intermediate status values (no per-stage progress display, no mapping of `BankUI` etc. to UI text) — the vocabulary is now fully enumerated (see Context), but only the three terminal states are acted on; intermediates carry no decision-relevant information for BankTeller.
- Unbounded confirmation retry — the automatic retry is bounded (2-minute budget, D5); beyond it the mismatch surfaces via the manual fallback. (The original no-retry stance was abandoned after live testing confirmed the whitelist lag is normal EB behavior, not a wrong assumption — see Context.)
- Handling hypothetical terminal states beyond the enumerated three — the vocabulary is closed (dynamic-dispatch reverse-engineering), so no further terminal values exist to discover; if EB ever adds one, their own frontend would throw on it, making it visible in their release notes or breakage.

## Decisions

**D1 — Poll server-side, not from the SPA.** The tilisy endpoint is a same-origin XHR for EB's own page; a browser call from the SPA would hit CORS. The SPA polls a BankTeller endpoint, which polls EB. Also keeps the sessionid server-side-only (it is a session capability — never logged, never sent to the client).

**D2 — Sessionid and poll base URL provenance: parse from the linking `authorization_url`.** The `POST /api/link-accounts` response's `authorization_url` carries `?sessionid=<uuid>` (verified). The server parses it at link time and stores **two** fields with the `linking_progress` stage data in the session cookie (ephemeral view-position data, same class as the bank triple — overwritten on every new link attempt, cleared with the stage): the `sessionid`, and the **poll base URL** (the `authorization_url`'s scheme + host). The base URL must be persisted because the poll endpoint needs it at cold-boot time — the `authorization_url` itself is returned to the SPA and never stored server-side, and the SPA holds no in-memory state after an F5, so without a persisted base URL the poll could not construct its request in the resume case (the change's own headline scenario). No new EB handshake, no extra request. The SPA never parses anything. Alternative rejected: a separate EB API call to create/lookup a session — no such documented API exists.

**D3 — Derive the poll URL's scheme+host from the linking `authorization_url`, never hardcode `tilisy.enablebanking.com`.** The poll URL is `<scheme+host of authorization_url>/ais/get_session_status`, with the scheme+host persisted at link time per D2 (never hardcoded). If EB completes the host migration, linking URLs and poll URLs move together. The path `/ais/get_session_status` is pinned (it is the endpoint we know).

**D4 — Minimal status interpretation over a now-enumerated vocabulary.** `AuthDone` → done; `Cancelled` → cancelled; `Invalid` → failed; any other status *value* (known intermediates, unknown values) → waiting. A **missing or unparseable `status` field is an error** (→ `unavailable`, the manual fallback) — response-shape drift is not an unknown value and must not be interpreted as "keep waiting". The vocabulary is closed by reverse-engineering (see Context: dynamic dispatch, exactly three terminal handlers), so the residual "unknown terminal value" risk is retired: any status EB's own frontend cannot handle makes *their* app throw, so a value BankTeller doesn't recognize is, with certainty, an intermediate. The server still logs every observed status value (info level, including unknowns) as a drift canary. Residual risk accepted (user decision, unchanged): if EB ever introduces a *new* terminal value, it maps to waiting indefinitely — but the user is never trapped: completing the process at EB's side always yields `AuthDone`, an F5 restarts the poll (a broken poll degrades to the manual screen), and the back-to-bank-list escape hatch reaches the resume card, which offers the same continuation the manual button would.

**D5 — Done state → whitelist confirmation with bounded server-side retry (reworked after live testing).** Live testing confirmed the ordering race (see Context): the tilisy status flips to `AuthDone` strictly before the whitelist reflects the new link, so a single-shot confirm loses the race in the common case and the original no-retry stance would have made the auto-advance useless — the whole point of the change. Rework: on the first `AuthDone` observation the endpoint stores a sticky in-memory marker keyed by sessionid (first-observed timestamp, next-due timestamp, result) and runs the whitelist confirm immediately. While the marker is active, subsequent polls **skip the tilisy call entirely** — the marker is the session's state, which also makes the design robust against the tilisy session being cleaned up after `AuthDone` (unknown today). Confirm attempts returning not-linked for the stage's bank, or failing (control-plane network errors included — they consume a retry, they are not `unavailable`), are retried on a backoff schedule — 5s, 10s, 20s, 40s, capped at 40s — within a **2-minute budget** from first observation (~6 attempts); the SPA keeps its dumb 5s cadence and the server decides per-request whether a confirm is due (a call before the next-due timestamp returns `confirming` without running a check). Confirm success → `done` (sticky, the auto-advance signal). Budget exhaustion → `unconfirmed` (sticky) — the manual button appears after two minutes of automatic attempts instead of on the first lost race; the mismatch remains visible (state + logs), just not prematurely. The confirmation matches the **stage's bank** (`aspsp_name` + `aspsp_country` from the stored view-position triple) against the whitelist — mirroring the link-status endpoint's filtered mode — so a whitelist entry for a different bank does not confirm this session. The marker is top-level in-memory state keyed by sessionid: a new link attempt stores a new sessionid (orphaning the old marker), entries expire (15-minute TTL) and are removed on read when expired (and swept on insert), so the map does not accumulate dead markers, and tests clear the map via a hook (mirroring `clearWhitelistCacheForTests()`). Residual unrecoverable case: the user closes the linking tab between the bank's success page and the redirect reaching the EB callback — the callback may never fire, no retry succeeds, and the budget exhaustion hands over to the manual fallback; the re-open affordance remains available during `confirming` because re-opening the authorization URL re-enters EB's `AuthDone` redirect, potentially completing the missing callback.

**Dead-session rule (added after live testing):** the whitelist outranks any failure-reporting AIS signal. The tilisy session is cleaned up after completion, and the marker is in-memory — so a page refresh or server restart after a successful link loses the marker and the next poll reads the dead session (`Invalid`, or `INVALID_SESSION`/network error). On `Invalid` the endpoint runs a fresh whitelist confirm first: stage's bank linked → `done` (auto-advance — no false failure panel); not linked → `failed`; whitelist unreachable → `unavailable`. In the Error branch the CACHED whitelist snapshot (primed by the SPA's cold-boot `/state` call) promotes the result to `done` when it proves the stage's bank linked — no fresh fetch there (the AIS call already failed; the manual check button resolves ambiguity). No marker/retry in these branches: the session is dead, no retry can ever succeed.

**Stage-promotion rule (added after live testing):** the session state always only ENHANCES the server state, it never replaces it. The route resolver honors a stored `linking_progress` stage only while `linking_completed == false` (the linking-page resume is the enhancement over ActivationGuide / the resume card, which is all the EB-side state alone could infer). Once the server side can tell linking has completed, the user routes to the auth step immediately — no matter that the fine-grained stage says the linking page was last shown: when the stage's bank is the linked one, the stage PROMOTES the route to `auth_progress` (the stage triple feeds the auth step exactly like a stored `auth_progress` stage — same coarse server-state level, refined by the session data); when the stage's bank is not linked (an in-flight link of a different bank), the stage is ignored and the ladder falls through to the resume card for the linked bank (authorizing the unlinked stage bank would fail at EB's side). This supersedes the earlier "explicit new link beats the resume card" stance: a cold boot resolves the correct step before any screen renders — no linking-page flash, no poll round-trip needed. The dead-session rule above remains as a second line of defense for the in-session case (a server restart while the page stays open).

**D6 — Poll cadence: every 5 seconds, no cap.** Matches the AIS app's own polling cadence class; the endpoint is lightweight (no auth dance, no rate-limit guidance exists for it). No poll cap: the user may leave the tab open overnight — consistent with the email-link waiting phase, which also polls indefinitely. Polling stops on: any received terminal state (`done`, `unconfirmed`, `cancelled`, `failed`, `unavailable`), leaving the step (cancel-linking, navigation), and view-model disposal. A **transient failure of the poll request itself** (network blip, timeout) does NOT stop the loop — the SPA keeps polling, and only a received `unavailable` state ends it (mirroring the registration-progress poll convention); a single dropped request must not silently strand the user on the manual screen. The `confirming` state is not terminal — the SPA keeps its cadence through it (the server absorbs the confirmation retry schedule per D5; the SPA never changes cadence).

**D7 — Fallback-first degradation.** Poll unavailability (network error, non-200, `INVALID_SESSION`, unparseable response) is reported as `unavailable`; the SPA silently renders today's static manual screen (explainer + re-open link + the mode-dependent forward action: "Open linking page" in the fresh entry, manual check button once the tab has been opened). No error banner — the user cannot fix EB's internals and the manual flow is fully functional. The manual check button and `GET /api/onboarding/link-status` endpoint remain untouched as the fallback path.

**D8 — Cancelled and Invalid mirror the auth-failure pattern with distinct error kinds.** The auth flow already differentiates callback failures into coarse-grained kinds (`classifyAuthError` in `OnboardingRoutes.kt`: `access_denied` → `cancelled`, `server_error`/`temporarily_unavailable` → `technical`, …) and renders kind-keyed copy in the AuthProgress failure panel. The linking flow maps onto the same two user-facing kinds: `Cancelled` → the `cancelled` kind (the raw EB response literally carries `error=access_denied` — the same OAuth code traveling through a different channel), `Invalid` → the `technical` kind (EB's own handler renders "Unable to authenticate" — a server-side failure where the user did nothing wrong). Both render an error-tinted panel (same pattern as the AuthProgress failure panel) with kind-specific copy and a "Try linking again" action calling `relinkAccount()` — which fetches a fresh `authorization_url` (hence a **new sessionid**, which the server stores, overwriting the old one) and returns the step to the waiting state. Polling stops in either failure state and restarts against the new sessionid on retry. Copy nuance: auth's cancelled copy says "cancelled at your bank" — for linking the cancellation happens at EB's consent screen, so the linking copy says so ("cancelled before it was completed; no accounts were linked"). Two documented windows: (a) **re-link mid-poll** — between a re-link POST's start and completion, a poll may still read the *old* sessionid and transiently report `unavailable` or a failure state; since those states are terminal (the loop stops), recovery is not "the next poll" but the retry flow itself: the poll job stays stopped while the re-link POST is in flight and restarts on its success against the new sessionid (a stale terminal reading cannot re-show the failure panel mid-retry). (b) **Concurrent link attempts** (double-click, two tabs): the last stored sessionid wins; the superseded EB session is orphaned and expires at EB's side — harmless by intent.

**D9 — UI per designer consultation (des-2; forward-slot placement per user testing, confirmed by des-2).** Seven states within the existing `WizardScaffold` frame. The footer's primary forward slot is a function of the poll state AND the tab-opened flag — the step's main action lives in the forward slot, per the wizard pattern's forward-momentum contract (every other step carries its primary action there; body placement made the single most critical action read as optional):

| poll state | tab not yet opened (fresh) | tab opened / resume |
|---|---|---|
| `waiting` | "Open linking page" (standard `ActionButton`) | empty — spinner layout |
| `confirming` | — (unreachable) | empty — spinner layout, confirming copy |
| `unconfirmed` | — (unreachable) | "I've completed linking" |
| `unavailable` | "Open linking page" | "I've completed linking" |
| `cancelled` / `failed` | — (unreachable) | "Try linking again" |
| `done` | transient — auto-advance | transient — auto-advance |

(1) waiting — standard 32dp brass hairline spinner (`WaitingIndicator`), heading "Waiting for you to complete the linking steps…", reassurance copy, "Re-open linking page" as a `QuietActionButton` inside a Tier-4 info box; the forward slot is empty once the tab has been opened (precedent: the email-waiting step's footer carries only its back action — an empty forward slot communicates "the ball is in your court in the other tab"; no layout collapse, the footer row keeps its standard height); (1b) confirming — the same spinner layout as waiting; the heading and reassurance switch to the completed-but-confirming copy ("Linking completed — confirming the connection…", "This usually takes just a few seconds."), because the original waiting copy ("Waiting for you to complete the linking steps…") is stale the moment the user has completed them — showing it for a potentially 30+-second window risks "did my completion not register?" panic; the re-open affordance stays available (re-opening the linking page re-enters EB's `AuthDone` redirect — the recovery path when the tab was closed before the callback fired); forward slot empty; (2) done-confirmed — no intermediate UI, direct step transition with the standard fade; (3) done-unconfirmed — manual check button in the forward slot + honest explainer; (4) cancelled — error DecisionBox, `cancelled`-kind copy, + "Try linking again" in the forward slot; (5) failed (`Invalid`) — error DecisionBox, `technical`-kind copy, + "Try linking again" in the forward slot (same structure as (4), different copy per D8); (6) unavailable — the manual screen composed mode-dependently (fresh mode: "Open linking page" in the forward slot + new-tab explainer; resume/re-open mode: resume one-liner, re-open quiet action, manual check button in the forward slot). The fresh-entry "Open linking page" button is a standard forward `ActionButton` exactly matching the other steps' forward buttons — no special styling, no external-link icon (per the design language: no speculative iconography; the copy already describes the outcome). The failure panels (4, 5) carry only the "Try linking again" action — no re-open affordance (the accidental-close info-box copy is incongruous on a failure panel and would duplicate the retry's effect); the re-open affordance is available in the waiting, confirming, unconfirmed, and unavailable states. The wizard one-liner switches with the tab-opened flag (fresh: redirect explanation ending "click below to open the connection page in a new window"; opened: "Complete the connection in the Enable Banking window. This page will advance automatically once confirmed.") so the forward button's disappearance is explained by the visible content change — no vanishing-button glitch. Popup-blocking is unaffected: the footer click is a direct user gesture, `window.open` inside the handler is equally popup-blocker-safe as a body click. Motion: constant-rate spinner, no copy pulsing on poll ticks; the spinner keeps running through the confirming state (the whitelist confirmation is server-side — there is no in-situ hold anymore).

**D10 — Copy constraint: no claims about closing the tab or returning later.** Mid-linking state is not recoverable after session expiry (server-side indistinguishable from "bank selected" — the resolver routes to the resume card, not back here). The waiting screen's copy is true in every reachable situation: the page waits indefinitely and advances on confirmation. The recovery card's re-open link covers accidental tab-close without promising anything about returning later.

## Risks / Trade-offs

- [Undocumented endpoint changes or disappears] → Fallback-first design (D7): any poll failure degrades to today's manual UX; the feature is progressive enhancement. The server logs observed status values, so semantic drift is discoverable.
- [Host migration breaks the hardcoded expectation] → D3 derives scheme+host from the `authorization_url`; only the path is pinned.
- [Whitelist lags `AuthDone` (confirmed by live testing, no longer hypothetical)] → D5: the sticky marker plus bounded backoff retry absorbs the (milli-)second-scale lag automatically; only a genuinely failed confirmation (2-minute budget exhausted, e.g. the linking tab closed before the EB callback fired) surfaces the manual button — the mismatch remains visible to the user and in logs.
- [Unknown status values with terminal semantics] → Retired by reverse-engineering: the vocabulary is closed (dynamic dispatch, exactly three terminal handlers — see Context), so an unrecognized value is with certainty an intermediate. If EB ever introduces a new terminal value, their own frontend throws on it, making the change visible; until BankTeller adapts, the step keeps waiting and the user is not trapped (completing the process at EB's side always yields `AuthDone`; an F5 restarts the poll; the back-to-bank-list escape hatch reaches the resume card, which offers the same continuation the manual button would). Unknown values are still logged as a drift canary.
- [Response-shape drift (missing/unparseable status field)] → Treated as an error → `unavailable` → manual screen (D4) — shape drift is never interpreted as "keep waiting".
- [Sessionid is a capability token] → Server-side only, never sent to the SPA, never logged, stored in the ephemeral session-cookie stage data with the same lifetime as the stage itself.
- [Polling load on EB] → 5s cadence, single in-flight linking session per user, single-user app by design; the endpoint serves EB's own UI at a similar cadence. No rate-limit guidance exists for it; if EB ever throttles, the failure path degrades to manual.
- [User leaves tab open forever] → Accepted by explicit product decision (mirrors email-link waiting); polling stops on step exit and view-model disposal.

## Migration Plan

Single-container deploy; no data migration. The session cookie's stage data gains optional sessionid and poll-base-URL fields — old cookies without them simply have no sessionid/base URL: the poll endpoint reports `unavailable` and the SPA shows the manual screen until the next `POST /api/link-accounts` writes a fresh stage with both fields. Rollback = redeploy previous image; no persisted state to unwind.

## Open Questions

None blocking. The status vocabulary is closed (reverse-engineered from the Tilisy AIS frontend bundle — see Context), so the former follow-up candidates are resolved: no further terminal states exist to promote, and per-stage progress display remains out of scope by choice (intermediates carry no decision-relevant information for BankTeller).
