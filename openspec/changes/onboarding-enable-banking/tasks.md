## 5. Onboarding Server Service, Routes, and Callback

- [ ] 5.1 Implement `OnboardingService` — manages short-lived in-memory onboarding contexts, each keyed by a per-flow random `state` token AND bound to the authenticated BankTeller user's session ID. Each context holds: email, the server-derived redirect URL used for the GIT `continueUrl` (returned to the SPA for informational display), captured `oobCode` (null until callback), and a status field (`PENDING` | `CALLBACK_RECEIVED` | `COMPLETED` | `FAILED`). Environment, user-confirmed redirect URL, and production field overrides are NOT stored in the context — they are passed in the completion request body and used directly. See design D9 — the `state` token provides flow correlation (cross-device) AND CSRF defense
- [ ] 5.2 Implement `getStatus()` — checks `system_config` for `enable_banking_application_id` + `enable_banking_private_key`; if present, calls `EnableBankingClient.verifyApplication()` with short-lived caching; returns `{enableBankingConfigured, verified, active}`
- [ ] 5.3 Implement redirect URL derivation — read `X-Forwarded-Proto` (fall back to request scheme) and `X-Forwarded-Host` (fall back to `Host`), produce `<scheme>://<host>/enable-banking-callback`
- [ ] 5.4 Implement `startOnboarding(email, callingUserSessionId)` — generate random `state` token; persist onboarding context (email, status=`PENDING`) bound to `callingUserSessionId`; derive the redirect URL from the calling request's forwarded headers; call `ControlPlaneClient.getOobConfirmationCode` with `continueUrl` = `<derived-redirect-url>?state=<token>`; return the `state` token AND the derived redirect URL (so the SPA can display it at the EmailEntry step as informational text)
- [ ] 5.5 Implement `GET /enable-banking-callback` route (unauthenticated) — validate `state` against persisted contexts; on valid `state`, store `oobCode` on the context, set status=`CALLBACK_RECEIVED`, and render an HTML "return to your original BankTeller tab" page; on invalid `state` or missing `oobCode`, render an error page without storing anything
- [ ] 5.6 Implement `completeOnboarding(state, callingUserSessionId, environment, redirectUrl, productionFieldOverrides?)` — validate the `state` belongs to `callingUserSessionId` (return 403 on mismatch — multi-user future-proofing); validate context status is `CALLBACK_RECEIVED` (error if `PENDING`/not found); call `emailLinkSignin` to get `idToken`; for PRODUCTION environment, auto-derive the `description` (BankTeller default), `gdpr_email` (user's entered EB email), `privacy_url` (`<redirect-url-host>/privacy`), `terms_url` (`<redirect-url-host>/terms`) per design D13, applying any overrides from the request body; call `KeyPairGenerator`; call `ControlPlaneClient.registerApplication` with `idToken`, cert, environment, application name, the user-confirmed `redirectUrl`, and (for PRODUCTION) the derived description/gdpr_email/privacy_url/terms_url; persist `application_id` + private key + `redirectUrl` in `system_config`; call `verifyApplication` to check `active`; set status=`COMPLETED`; return success/failure with `active` status; on any step failure, do not persist credentials, set status=`FAILED`
- [ ] 5.7 Implement `GET /api/onboarding/enable-banking/redirect-url` route (authenticated) — returns the derived redirect URL for the SPA to display in the RegistrationReview step as a pre-filled editable field
- [ ] 5.8 Implement `POST /api/onboarding/enable-banking/start` route (authenticated) — accepts ONLY email (no environment, no redirect URL, no production fields — all deferred to the completion step per design D13/D8 reorder); validates email format; calls `startOnboarding` with the calling session ID; returns the `state` token AND derived redirect URL in the response
- [ ] 5.9 Implement `GET /api/onboarding/enable-banking/wait?state=<token>` route (authenticated) — validates the `state` belongs to the calling user (403 otherwise); returns `{"status":"pending"}` if context status is `PENDING`, or `{"status":"complete"}` if `CALLBACK_RECEIVED`
- [ ] 5.10 Implement `POST /api/onboarding/enable-banking/complete` route (authenticated) — accepts `state` token, `environment`, `redirectUrl`, and optional `productionFieldOverrides` (for PRODUCTION) in the body; calls `completeOnboarding` with these and the calling session ID; handles state-not-found, state-belongs-to-other-user, callback-not-yet-received, GIT-login-failed, registration-failed, verification-failed error cases with clear messages
- [ ] 5.11 Implement `GET /api/onboarding/status` route (authenticated) — returns `OnboardingService.getStatus()` result
- [ ] 5.12 Register `/api/onboarding/*` routes under the existing session-validation middleware; register `/enable-banking-callback` as an unauthenticated public route
- [ ] 5.13 Implement static privacy and terms pages served at `/privacy` and `/terms` (unauthenticated, public) — placeholder content for now; possibly combined into a single page reachable at both paths. Used as `privacy_url` and `terms_url` for PRODUCTION registration per design D13

## 7. SPA Onboarding Gate

- [ ] 7.1 Add `Onboarding` value to the `Screen` enum in `:app:web` (no navigation library introduced)
- [ ] 7.2 Extend `AppViewModel` — after successful auth check, call `GET /api/onboarding/status`; if `enableBankingConfigured` is false OR `verified` is false, set `currentScreen = Onboarding` (at the email-entry step); if `active` is false, set `currentScreen = Onboarding` (at the activation guide step); otherwise set `Dashboard`
- [ ] 7.3 Implement `OnboardingScreen` composable with multi-step state machine: EmailEntry → WaitingForAuthentication → RegistrationReview → Verifying → ActivationGuide (only when active=false). The state machine stores the `state` token received from `POST /start` after the EmailEntry step
- [ ] 7.4 Implement the EmailEntry step — form field for Enable Banking email ONLY (no environment, no redirect URL, no production fields — all deferred to RegistrationReview per D8 reorder/D13); display the server-derived redirect URL as informational text ("BankTeller will use `<derived URL>` for the email-link redirect — fix your reverse proxy config if this looks wrong"); on submit, call `POST /api/onboarding/enable-banking/start` with the email, store the returned `state` token AND derived redirect URL in the view-model, and transition to the WaitingForAuthentication step
- [ ] 7.5 Implement the WaitingForAuthentication step — "check your email" message, hint that the user may click the email link on another device and this tab will auto-advance, display of the derived redirect URL that was used (with a "something wrong?" troubleshooting hint so the user can spot a misconfigured proxy if the email-link click never arrives), and a polling loop that calls `GET /api/onboarding/enable-banking/wait?state=<token>` every 1-2 seconds (with backoff). When the response is `{"status": "complete"}`, auto-advance to the RegistrationReview step. There is no explicit "complete now" button — the user already initiated by entering email
- [ ] 7.5a Implement the RegistrationReview step (covers all registration-time inputs together, per D13) — fetch the derived redirect URL from `GET /api/onboarding/enable-banking/redirect-url` to pre-fill the editable field; show an environment selector (defaulting to PRODUCTION — production access is what users typically want) with inline help text (or a tooltip via an info icon next to each option) explaining what each environment means per design D13 (PRODUCTION: real bank accounts + manual "link at least one account" step + non-transferable; SANDBOX: simulated banks + auto-activated + non-transferable); show the redirect URL field (editable, pre-filled with the derived value); when environment=PRODUCTION is selected (the default), reveal the auto-derived `description`, `gdpr_email` (the user's entered EB email), `privacy_url` (`<redirect-host>/privacy`), `terms_url` (`<redirect-host>/terms`) — all editable; on submit, call `POST /api/onboarding/enable-banking/complete` with the `state` token + environment + redirect URL + (PRODUCTION only) production fields, and transition to the Verifying step
- [ ] 7.6 Implement the Verifying step — pending state during the completion call (GIT login, key generation, registration, verification); on success with `active: true`, dismiss the gate and render the dashboard; on success with `active: false`, transition to the ActivationGuide step; on error, show the error with a "restart onboarding" action
- [ ] 7.7 Implement the ActivationGuide step — single instruction to link at least one account on the Enable Banking control panel, with a direct link to `https://enablebanking.com/cp/applications`; explain that for personal-use registrations, linking an account both activates the app and grants that account API access (per EB FAQ); the gate will close automatically on the next login once `active` becomes true
- [ ] 7.8 Ensure there is no navigation entry that re-opens onboarding while credentials remain valid and active; the gate is reachable only via the missing/invalid/inactive-credentials condition
- [ ] 7.9 Handle polling lifecycle correctly — suspend polling when the SPA is hidden/inactive, resume on focus; abort polling cleanly if the user navigates away or starts a new onboarding attempt (avoid leaked coroutines)
