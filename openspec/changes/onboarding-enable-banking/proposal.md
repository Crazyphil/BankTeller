## Why

The foundation change shipped a bootstrapped BankTeller (login, DB, Docker, SPA shell) with no way to connect to Enable Banking — the linchpin dependency for every business feature. Before the system can sync accounts, evaluate workflows, or prepare payments, it must establish a functional, verified Enable Banking application (a registered app identified by an `application_id` with a matching RSA private key).

This change adds the Enable Banking client foundation and a fully automated first-run onboarding flow that registers a new Enable Banking application on the user's behalf. The user enters their Enable Banking email, clicks a login link, and BankTeller handles the rest: captures the authentication token via a local callback, generates the RSA key pair and X.509 certificate in-app, registers the application through Enable Banking's control-plane API, stores the returned `application_id` and private key, and verifies everything via `GET /application`. For production apps, BankTeller also detects whether the application still needs the one manual "Activate by linking accounts" step on the Enable Banking control panel and guides the user through it.

This is the only onboarding path. A manual fallback (paste `application_id` + key generated via `openssl`) is deliberately not implemented — the automated path matches Enable Banking's own official CLI tooling and is the sole user experience.

## What Changes

- **Enable Banking HTTP client** (`:server`): PKCS#8 PEM private key loading, RS256 JWT builder (header `kid=application_id`, body `iss=enablebanking.com`, `aud=api.enablebanking.com`, `iat`, `exp`; regenerated per request), Ktor `HttpClient` with a Bearer auth interceptor that signs each outgoing request, and a `GET /application` call used to verify credentials and check the `active` field. Data-plane endpoint only (`api.enablebanking.com`).
- **Enable Banking control-plane client** (`:server`): calls `POST https://enablebanking.com/api/applications` using a Firebase `idToken` (obtained via the Google Identity Toolkit email-link flow) as the Bearer token to register a new application, submitting an in-app-generated X.509 certificate, the chosen environment (SANDBOX or PRODUCTION), an application name, and the user-confirmed redirect URL (derived by default from the request's forwarded headers, with an in-flow override for non-standard proxy setups). Returns and stores the `application_id`.
- **Google Identity Toolkit (GIT) integration** (`:server`): implements Enable Banking's email-link login flow (the same flow used by Enable Banking's official Python CLI) by calling the Google Identity Toolkit REST endpoints — `createAuthUri` / `getOobConfirmationCode` to request a login link, then `emailLinkSignin` to exchange the `oobCode` (captured from the email-link callback) for a Firebase `idToken`. The Firebase `idToken` is used only for the application-registration call and is discarded after registration; no refresh-token persistence in this change.
- **Callback handler** (`:server`): an unauthenticated `/enable-banking-callback` route that Enable Banking's email-link flow redirects the user's browser to with `?oobCode=...&state=<token>`. The route validates the `state` token against a persisted onboarding context (bound to the authenticated BankTeller user who started the flow), stores the `oobCode` keyed by that `state`, and renders a simple HTML page telling the user to return to their original BankTeller tab to continue (it will auto-advance). The route is unauthenticated (the foundation's `SameSite=Strict` session cookie is not sent on cross-site navigations, so the callback cannot rely on the cookie); the `state` token provides flow correlation (cross-device support) and CSRF defense (unforgeable secret in the email link). The privileged completion endpoint requires an authenticated session AND validates that the `state` belongs to the calling user — multi-user safe. This route is owned by this change and will be extended by the future bank-connection change to handle PSU consent callbacks.
- **In-app RSA key pair + X.509 certificate generation**: 4096-bit RSA private key (PKCS#8 PEM) and matching self-signed X.509 certificate generated inside BankTeller (BouncyCastle) so the user never runs `openssl`. The certificate is the only value transmitted to Enable Banking; the private key never leaves BankTeller.
- **Credential persistence in `system_config`**: three new rows — `enable_banking_application_id` (UUID), `enable_banking_private_key` (PEM string), and `enable_banking_redirect_url` — reusing the existing key/value infrastructure. No new tables, no migrations.
- **Credential provider abstraction**: an interface (`EnableBankingCredentialProvider`) with two implementations — a database-backed provider for production (reads `system_config`) and a static provider that returns committed shared sandbox credentials for integration tests. The HTTP client and JWT pipeline are environment-transparent (Enable Banking serves sandbox and production from the same `api.enablebanking.com` base URL; only the credentials differ).
- **Onboarding gate in the SPA** (shown when credentials are absent or `GET /application` reports the app is missing/invalid): a guided flow — enter Enable Banking email ONLY → BankTeller sends login link → user clicks link (possibly on another device) → BankTeller captures callback automatically via `state` token → SPA auto-advances to RegistrationReview step where the user chooses environment (defaulting to PRODUCTION — production access is what users typically want; SANDBOX is a deliberate opt-in for testing, with inline help text explaining each option per design D13), reviews and may override the pre-filled derived redirect URL, and (for PRODUCTION) confirms the auto-derived production fields (`description`/`gdpr_email`/`privacy_url`/`terms_url` per design D13) → BankTeller runs GIT login + key generation + application registration + `GET /application` verification → done. When the app exists but is not yet `active` (production only), the gate surfaces the single remaining manual step (link at least one account on the Enable Banking control panel) and re-checks `active` on subsequent logins. The gate is **not** a navigation item — it is a transient overlay driven by missing/invalid data, consistent with the VISION §5.5 "derived from actual data" principle.
- **No PSU/consent flow, no account data, no read endpoints**: `POST /auth`, `POST /sessions`, `GET /aspsps`, and all account/balance/transaction reads are explicitly out of scope. No account or session data is persisted by this change. This change establishes *application-level* Enable Banking connectivity only; PSU-level bank connection is a separate future change.

## Capabilities

### New Capabilities
- `enable-banking-client`: The client layer that authenticates to the Enable Banking data-plane API via RS256 JWT signing, loads PKCS#8 private keys, regenerates tokens per request, exposes `GET /application` verification (including the `active` field), and implements the Google Identity Toolkit email-link login flow used to obtain a Firebase `idToken` for control-plane application registration. Reusable by all future Enable Banking integrations (bank connection, sync engine).
- `onboarding`: First-run gate logic and server endpoints that detect missing/invalid Enable Banking credentials, drive the automated registration flow (email-link auth, key generation, app registration, verification), accept the callback, and expose onboarding status to the SPA. Does not cover notification setup or bank connection (future changes).

### Modified Capabilities
- `spa-shell`: Adds an onboarding gate screen rendered when Enable Banking credentials are missing or the application is not yet active/verified, layered over the existing dashboard. No navigation structure is introduced — onboarding is a transient gate, not a permanent destination.

## Impact

- **`:server`**: New `enablebanking/` package containing the data-plane HTTP client, JWT signer, PKCS#8 key loader, credential provider, and control-plane client (GIT flow + `POST /api/applications`). New `crypto/` helper for RSA key pair + self-signed X.509 cert generation via BouncyCastle. New `onboarding/` package with the onboarding service, routes (`/api/onboarding/*`), and the `/enable-banking-callback` route. `Application.kt` wires the credential provider, onboarding detection, and the callback route into startup and routing.
- **`:core`**: Unchanged. Domain DTOs (`Amount`, `Account`, etc.) are deferred to the bank-connection change where their shapes are derived from real Enable Banking responses. `GreetingUtil` is left in place.
- **`:app:web`**: New onboarding screen composable with a multi-step flow — EmailEntry (email only) → WaitingForAuthentication (polls wait endpoint) → RegistrationReview (environment selector + editable redirect URL + PRODUCTION-only auto-derived production fields, per D13) → Verifying → done / activation guide. `App.kt` routing gains an onboarding gate branch that renders before the dashboard when credentials are missing or the app is not active. No navigation component is added.
- **`system_config`**: Three new keys consumed (`enable_banking_application_id`, `enable_banking_private_key`, `enable_banking_redirect_url`); no schema migration required.
- **Dependencies**: New server dependencies — BouncyCastle (`bcpkix-jdk18on`) for X.509 certificate generation, and any transitively-available Ktor HttpClient engine. JWT signing uses JCE (`java.security`) directly — no external JWT library, and the official Enable Banking Java SDK is explicitly rejected (proprietary license, not on Maven Central, blocking I/O incompatible with Ktor coroutines, does not cover `GET /application` or the control-plane flow). No new SPA dependencies.
- **Tests**: A real-sandbox integration test (using committed shared sandbox credentials) exercises the data-plane JWT pipeline and `GET /application`. Unit tests with mocked HTTP responses cover the control-plane registration flow, the GIT auth flow, and edge cases (inactive app, 401, malformed callback) that cannot be reproduced against the always-active sandbox. CI fails the build if the integration test cannot reach `api.enablebanking.com` (GitHub Actions has outbound network access).
- **No breaking changes** to existing auth, session, or SPA behavior — the onboarding gate and callback route are additive.
