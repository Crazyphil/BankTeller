## Context

The archived onboarding change (`2026-08-06-onboarding-enable-banking`) registered the Enable Banking application (control-plane `POST /api/register`) and implemented the email-link authentication flow, but stopped there. The registered application has no whitelisted PSU accounts and no AIS session — so no account data can be read.

This change implements the remaining two steps required before AIS reads become possible:

1. **Account linking** (control-plane `POST /api/link_accounts`, Firebase idToken auth): Whitelists the PSU's account on the application. The PSU is redirected to an Enable Banking control-panel page where they authorize the application to access their bank. Returns a `psu_id_hash` that identifies the whitelisted account. Completion is detected by checking `GET /application` for a matching `psu_id_hash` in `whitelisted_accounts[].identification_hash`.

2. **Session authorization** (data-plane `POST /auth` → bank SCA → `POST /sessions`, RS256 JWT auth): Creates a user session for reading account data. The PSU is redirected to their bank for SCA. After completing SCA, the bank redirects back with a `code`, which is exchanged via `POST /sessions` for a `session_id` + `accounts[]`.

Both are required per account. Linking without auth produces an active app with no usable session; auth without linking produces a session that can't access any account data.

**Enable Banking reference implementations**: There is no official reference library from Enable Banking. The `enablebankinggo` repo (https://github.com/marefr/enablebankinggo) is a **community/unofficial** Go client that demonstrates the control-plane and data-plane flows (including account linking) and is useful as a reference for request/response shapes — but it is not maintained by Enable Banking as an official SDK. Additional samples in various languages plus the `enablebanking-cli` client are at https://github.com/orgs/enablebanking/repositories.

**Dashboard scope**: This change does **not** modify the dashboard. Completing onboarding (linking + auth) simply forwards to the existing dashboard. The dashboard content has not been specified yet and will be refactored in a follow-up change. This change delivers the linking + auth/session infrastructure only.

### Settled Decisions

**D1 — Auth/session only, no AIS reads.** This change implements `POST /auth`, `POST /sessions`, and the link-completion check. It does **not** implement AIS reads (`GET /accounts`, `GET /transactions`, balances, transactions display). Those are a separate concern (data modeling, pagination, categorization) and belong in a follow-up change.

**D2 — Reuse the existing `GET /enable-banking-callback` route for auth returns.** The route already handles the GIT email-link callback (query param `oobCode`). It is extended to also handle the EB auth callback (query param `code`). Distinguishing logic: if `oobCode` is present → email-link flow (possibly different device, no session cookie expected); if `code` is present and `oobCode` is absent → auth flow (same browser tab, session cookie present, verify auth before continuing). This difference matters: the auth callback runs in the same browser tab that started the process, so the session cookie is available and must be verified before proceeding.

**D3 — No fallback re-authentication.** The refresh token is validated at login (the login step calls `refreshIdToken` to confirm it works). A fresh idToken is obtained proactively before every control-plane request. Since a fresh idToken is always used, 401 responses are not expected and no retry/fallback pattern is implemented. `refreshIdToken` owns the full refresh-token lifecycle: on success it persists the (possibly rotated) refresh token to `system_config`; on failure (invalid/expired/revoked) it clears the token from `system_config` so the next onboarding-state check routes the user to re-login (the user re-does only the email-link login step — `application_id` and `private_key` remain valid). Transient errors (network, 5xx) do NOT clear the token — it may still be valid on retry.

**D4 — No background polling for link completion.** Linking opens a new browser tab (EB control panel). Instead of polling `GET /application` in the background, the original tab shows an explanatory message and a button ("I've completed linking, authorize now"). When clicked, the SPA does a single check (`GET /api/onboarding/link-status`) to confirm linking succeeded, then proceeds to auth. Rationale: (a) the user has time to read the two-step explanation, (b) no confusion from a second redirect appearing while the first tab is still open, (c) less load on the EB API.

**D5 — No server-side ASPSP filtering.** The server fetches all ASPSPs from `GET /aspsps` and returns them unfiltered. Filtering (by search text, country, PSU type) happens client-side in the SPA.

**D6 — `link_accounts` redirect_url is a fixed constant.** The control-plane `POST /api/link_accounts` requires a `redirect_url` parameter, but external redirect URLs do not work — the value must point to Enable Banking's own control-panel callback. The exact value is `https://enablebanking.com/api/auth_redirect` (confirmed from the `marefr/enablebankinggo` reference client, `controlpanel/application_operations.go:129`). This is shipped as a **code constant** in `EnableBankingControlPlaneClient` (not stored in `system_config` — it is not user-configurable and not environment-specific). Only the data-plane auth callback URL (`enable_banking_redirect_url`) is customizable and stored in `system_config`.

**D7 — `refreshIdToken` owns the full token lifecycle.** `refreshIdToken` persists the (possibly rotated) refresh token to `system_config` on success and clears it on failure (invalid/expired/revoked). This centralizes token persistence in the method that owns the token — no calling route needs to persist or clear the token separately. Transient errors (network, 5xx) do NOT clear the token — it may still be valid on retry. When the token is cleared, the next `GET /api/onboarding/state` check detects the missing token and routes the user to re-login (the user re-does only the email-link login step — `application_id` and `private_key` remain valid).

**D8 — Resume flow via `GET /api/onboarding/state`.** The SPA calls `GET /api/onboarding/state` on load to determine the current onboarding progress and route to the correct step. This handles three interrupt scenarios: (a) the user opened a new tab while the original tab was at the bank's SCA page — the new tab shows the LinkingProgress screen with a "Continue to authorization" button; (b) the auth callback failed (invalid code, bank denied, technical error) — the SPA shows the LinkingProgress screen with the error message and a retry button; (c) the auth callback arrived without a session cookie — the server 302 redirects to the BankTeller login page (username/password, not the Enable Banking email-link flow), discards the single-use `code`, and after re-login the SPA resumes via the state check. In all cases, the user can re-initiate auth cleanly from the LinkingProgress screen. The original bank `code` is single-use and time-limited, so it cannot be reused after an interrupt — the user starts a fresh `POST /api/auth` instead.

**D9 — `auth_error` is ephemeral user-session state, cleared on new auth attempt.** The `auth_error` (stored when an auth callback fails) lives in the **BankTeller user session** — the session associated with the session cookie. It is NOT persisted to `system_config` or a database. This is distinct from `enable_banking_refresh_token` (which lives in `system_config` because it must survive logout). The `auth_error` dies with the session (logout, expiry). It is cleared at **two points**: (1) when `POST /api/auth` is called — the user has acknowledged the error and is starting a fresh attempt, so the error is cleared at the start of the request (this prevents a stale error from appearing in a subsequently opened tab); (2) when the auth callback succeeds — belt-and-suspenders, since `POST /api/auth` already cleared it. The error is shown **exactly once**: on the LinkingProgress screen after a failed callback, and it disappears the moment the user clicks "Continue to authorization". Without clearing point (1), a user who clicks "Continue to authorization" and then opens a new tab while at the bank's SCA page would see the old error in the new tab — even though they've already moved past it.

**D10 — Routing flags, not string parsing.** The state endpoint's response separates **routing flags** (`requires_relogin`, `linking_completed`, `auth_completed`) from **display-only fields** (`auth_error`, `selected_bank`). The SPA determines routing exclusively from the flags — it never parses `auth_error` string values for control flow (e.g. no `auth_error === "refresh_token_missing"` check to decide re-login). Re-login is signaled by the dedicated `requires_relogin` bool, which is true iff `enable_banking_refresh_token` is missing from `system_config`. String parsing for control flow is fragile — adding a new error reason or rewording a message would silently break routing. The `selected_bank` object is returned so the SPA can pass the bank identifier to `POST /api/auth` in the resume flow — after a reload (new tab, failed callback), the SPA no longer has `{aspsp_name, aspsp_country, psu_type}` in viewmodel state, and `POST /api/auth` requires them in the request body. The bank info is stored in the user session by `POST /api/link-accounts` (the same call that stores `psu_id_hash`).

### Onboarding Flow

The SPA onboarding gate (`OnboardingScreen.kt`) gains these steps in order:

1. **ActivationGuide** (modified): Explains that what follows is a **two-step process** where the user authorizes with their bank **twice** — first to link their account (in a new tab), then to create a session (in the current tab). Both are required to provide free access to their accounts. The user clicks "Start Bank Setup" to proceed.

2. **BankSelection** (new): The SPA calls `GET /api/aspsps` (fetches all banks, no server-side filters). The user searches and selects their bank. On "Connect [Bank]", the SPA calls `POST /api/link-accounts`, receives an `authorization_url`, and opens it in a **new browser tab** (EB control panel).

3. **LinkingProgress** (new): The original tab shows a message explaining that the user should complete linking in the other tab, then click "I've completed linking, authorize now". **No background polling.** When the button is clicked, the SPA calls `GET /api/onboarding/link-status` (single check). If linking succeeded, proceed to AuthProgress. If not, show an error and let the user retry. **This screen is also the resume point** when the SPA loads and `GET /api/onboarding/state` returns `(requires_relogin=false, linking_completed=true, auth_completed=false)`: if the user opened a new tab during authorization, or the auth callback failed, the SPA shows this screen (with the error message if `auth_error` is present) and a "Continue to authorization" button so the user can re-initiate auth. Clicking the button triggers `POST /api/auth`, passing the `selected_bank` fields from the state endpoint response as the request body (the SPA doesn't have them in viewmodel state after a reload). The server clears `auth_error` from the user session at the start of that request — so the error is shown exactly once and does not follow the user into the new attempt or appear in a subsequently opened tab.

4. **AuthProgress** (new): The SPA calls `POST /api/auth`, receives an `authorization_url`, and redirects the **current tab** to the bank's SCA. After completing SCA, the user is redirected back to `GET /enable-banking-callback` with `code` + `state`. The callback verifies the session cookie (same tab → cookie expected); on missing cookie it 302 redirects to login (the `code` is discarded). On valid session, the callback decodes the session ID from `state` (JWT), calls `POST /sessions`, stores `session_id` + `accounts[]` in the user session (on success) or stores the error reason as `auth_error` in the user session (on failure), and serves the SPA bundle. On success, the SPA forwards to the dashboard. On failure, the SPA loads, calls `GET /api/onboarding/state`, and shows the LinkingProgress screen with the error and a retry button.

5. **Dashboard** (unchanged): The existing dashboard is shown as-is. Out of scope.

### API Designs

**`GET /api/aspsps`** (new, session-authenticated)

Proxies to `GET /aspsps` on the Enable Banking data-plane API (RS256 JWT auth — no Firebase token needed). No query parameters — all ASPSPs are returned unfiltered. Returns: `[{ "name", "country", "bic", "logo", "psu_types", "maximum_consent_validity" }]`. Banks are identified by the `{name, country}` pair — the Enable Banking API has no ASPSP UID. The `maximum_consent_validity` field (seconds) is used later to compute the maximum `valid_until` for `POST /api/auth`. Auth: BankTeller session cookie.

**`POST /api/link-accounts`** (new, session-authenticated)

Proxies to `POST /api/link_accounts` on the Enable Banking control-plane API (Firebase idToken auth). The server first calls `refreshIdToken(refreshToken)` to obtain a fresh idToken, then sends the request as `multipart/form-data`. Form fields (camelCase, matching the EB control-plane API): `country`, `aspsp`, `appId`, `psuType`, `redirectUrl`. The `redirectUrl` is the **fixed constant** `https://enablebanking.com/api/auth_redirect` (shipped in code, not `system_config`). Returns: `{ "authorization_url", "psu_id_hash" }`. The server stores the `psu_id_hash` **and the selected bank info** (`aspsp_name`, `aspsp_country`, `psu_type`) in the user session — the bank info is needed by `GET /api/onboarding/state` so the SPA can pass it to `POST /api/auth` in the resume flow (after a reload, viewmodel state is gone). Auth: BankTeller session cookie.

**`GET /api/onboarding/link-status`** (new, session-authenticated)

Checks whether linking has completed. Calls `GET /application` on the control-plane API (Firebase idToken auth, fresh idToken via `refreshIdToken`). Compares the `psu_id_hash` from the `link_accounts` response against `whitelisted_accounts[].identification_hash`. Returns: `{ "linked": true/false }`. This is a **single on-demand check** (triggered by the user clicking "I've completed linking"), not background polling. Auth: BankTeller session cookie.

**`POST /api/auth`** (new, session-authenticated)

Proxies to `POST /auth` on the Enable Banking data-plane API (RS256 JWT auth). Request body: `{ "aspsp_name", "aspsp_country", "psu_type", "access": { "valid_until", "balances": true, "transactions": true }, "state", "redirect_url" }`. The `aspsp_name` + `aspsp_country` identify the bank (the Enable Banking API identifies banks by the `{name, country}` pair, not a UID). The `state` is a JWT encoded server-side containing the BankTeller session ID. The `redirect_url` is read from `system_config` (`enable_banking_redirect_url`) — the BankTeller callback URL. The `valid_until` is set to the maximum allowed: `now + ASPSP.maximum_consent_validity` (fetched from `GET /api/aspsps` and cached). The `access` scope requests **balances and transactions** — these are the data types we need access to. Adding new access types later (e.g. payments) would require re-authorization. Returns: `{ "url", "authorization_id", "psu_id_hash" }`. **The server clears any stored `auth_error` from the user session at the start of the request** (the user is starting a fresh attempt — the old error must not follow them into the new attempt or appear in a subsequently opened tab). Auth: BankTeller session cookie.

**`GET /api/onboarding/state`** (new, session-authenticated)

Returns the current onboarding progress so the SPA can route the user to the correct step on load (including when the user opens a new tab during an in-progress flow, or after re-login following a missing session cookie). The server inspects the **BankTeller user session** (ephemeral, tied to the session cookie) and `system_config` and returns a structured response with routing flags and display-only fields (per D10): `{ "requires_relogin": bool, "linking_completed": bool, "auth_completed": bool, "auth_error": string|null, "selected_bank": object|null }`. `requires_relogin` is true iff `enable_banking_refresh_token` is missing from `system_config` (cleared by `refreshIdToken` on invalid-token failure) — the sole re-login signal; the SPA never parses `auth_error` for routing. `linking_completed` is true if a `psu_id_hash` is stored in the user session (from a prior `POST /api/link-accounts`). `auth_completed` is true if a `session_id` + `accounts[]` are stored in the user session (from a prior auth callback). `auth_error` holds the error reason stored in the user session if the last auth callback failed (e.g. "invalid code", "bank denied", "state mismatch"), or null — display-only. The `auth_error` is **ephemeral session state** — not persisted to `system_config` or a database, dies with the session (logout, expiry), and is cleared when the user starts a new auth attempt via `POST /api/auth`. This is distinct from `enable_banking_refresh_token` (which lives in `system_config` because it must survive logout). `selected_bank` is the bank info stored in the user session by `POST /api/link-accounts`: `{ "aspsp_name", "aspsp_country", "psu_type" }`, or null if linking has not been completed — the SPA needs this to call `POST /api/auth` in the resume flow (after a reload, viewmodel state is gone). Auth: BankTeller session cookie.

**`GET /enable-banking-callback`** (modified)

Extended to handle auth returns in addition to the existing email-link callback. Distinguishing logic:
- If `oobCode` is present: email-link flow (existing behavior, possibly different device, no session cookie expected).
- If `code` is present and `oobCode` is absent: auth callback. **Verify the session cookie** (same browser tab → cookie expected). On missing/invalid session cookie, **302 redirect to the BankTeller login page** (username/password login — not the Enable Banking email-link flow) and discard the `code` (single-use, time-limited — cannot be correlated to a new session after re-login); after re-login, the SPA resumes via `GET /api/onboarding/state`. On valid session, decode the session ID from `state` (JWT). Call `POST /sessions` on the data-plane API (RS256 JWT) with the `code`. On success (HTTP 200 — the Enable Banking `POST /sessions` response has no `status` field, so a 200 response is the sole success indicator), clear any stored `auth_error` from the user session (belt-and-suspenders — `POST /api/auth` already clears it at the start of a new attempt), store `session_id` + `accounts[]` in the user session, and serve the SPA bundle so the SPA can forward to the dashboard. On failure (non-200 from `authorizeSession`, or invalid `state` JWT), store the error reason as `auth_error` in the user session (so the SPA can display it on the LinkingProgress screen with a "Continue to authorization" retry button via the `GET /api/onboarding/state` resume flow — the error is cleared when the user clicks the button, via `POST /api/auth`) and serve the SPA bundle.

### UI Design

The UI was specified by @designer (session `des-3`), reviewing the existing Material 3 patterns in `OnboardingScreen.kt`, `LoginScreen.kt`, and `DashboardScreen.kt`. The design reuses the existing card-container, typography hierarchy, and button-placement conventions.

**ActivationGuideStep** (modified): `Card` container with `headlineSmall` header ("Complete Bank Setup") and `bodyMedium` body text explaining the two-step process — Step 1 links the account (new tab), Step 2 creates a session (current tab), both required for free account access. Primary `Button` ("Start Bank Setup", `fillMaxWidth()`) advances to `BankSelection`. Secondary `TextButton` ("Logout").

**BankSelectionStep** (new): `Card` container with `headlineSmall` header ("Select your bank"). `OutlinedTextField` for instant client-side search across bank name, country, and BIC. `LazyColumn` of bank items showing country badge (`bodySmall`), bank name (`bodyLarge`, bold), BIC (`robotoMonoFamily`), and `FilterChip` for PSU type. `CircularProgressIndicator` during initial load. Primary `Button` ("Connect [Selected Bank]", `fillMaxWidth()`, disabled until a selection is made). On `authorization_url` received, opens in a new tab and transitions to `LinkingProgress`.

**LinkingProgressStep** (new): `Card` container with `headlineSmall` header ("Complete account linking"). `bodyMedium` message instructing the user to complete linking in the other tab, then return here. Primary `Button` ("I've completed linking, authorize now", `fillMaxWidth()`) triggers `GET /api/onboarding/link-status`. On success → `AuthProgress`. On failure → `Text` error message with retry. No loading spinner beyond the brief status check. No background polling. **Resume mode**: when the SPA loads via `GET /api/onboarding/state` with `(requires_relogin=false, linking_completed=true, auth_completed=false)`, this screen is shown with a "Continue to authorization" button (label adapts to context). If `auth_error` is present (auth callback previously failed), an error `Text` is shown above the button with the reason (e.g. "Bank denied the authorization", "Invalid or expired code", "Technical error"). The button triggers `POST /api/auth` to start a fresh authorization, passing the `selected_bank` fields (`aspsp_name`, `aspsp_country`, `psu_type`) from the state endpoint response as the request body — the server clears `auth_error` from the user session at the start of that request, so the error is shown exactly once and does not follow the user into the new attempt or appear in a subsequently opened tab.

**AuthProgressStep** (new): `Card` container with `headlineSmall` header ("Authorizing session"). `bodyMedium` message explaining that the user will be redirected to their bank. The redirect to `authorization_url` happens automatically on entering this step (current tab, not a new tab). On return via callback, the SPA forwards to the dashboard.

### Out of Scope

- **AIS reads**: No `GET /accounts`, `GET /transactions`, balances, or transactions display. The session is created but not used for data reads in this change.
- **Dashboard changes**: The dashboard is untouched. Completing onboarding forwards to the existing dashboard.
- **Session refresh/renewal**: The `valid_until` is set to the maximum allowed by the ASPSP (`now + maximum_consent_validity`). No automatic renewal logic. Re-authorization flow (single-step re-auth for an existing linked account) is a future concern — this change only implements the initial two-step linking + auth flow.
- **Adding accounts after onboarding**: This change only handles the initial onboarding flow. Adding additional accounts later is a future concern.
- **Payment initiation**: No payment access scope. Only `balances` and `transactions` are requested.
