## 5. Onboarding Server Service, Routes, and Callback

- [x] 5.1 Implement `OnboardingService` — manages short-lived in-memory onboarding contexts, each keyed by a per-flow random `state` token AND bound to the authenticated BankTeller user's session ID. Each context holds: email, the server-derived redirect URL used for the GIT `continueUrl` (returned to the SPA for informational display), captured `oobCode` (null until callback), and a status field (`PENDING` | `CALLBACK_RECEIVED` | `COMPLETED` | `FAILED`). Environment, user-confirmed redirect URL, and production field overrides are NOT stored in the context — they are passed in the completion request body and used directly. See design D9 — the `state` token provides flow correlation (cross-device) AND CSRF defense
- [x] 5.2 Implement `getStatus()` — checks `system_config` for `enable_banking_application_id` + `enable_banking_private_key`; if present, calls `EnableBankingClient.verifyApplication()` with short-lived caching; returns `{enableBankingConfigured, verified, active}`
- [x] 5.3 Implement redirect URL derivation — read `X-Forwarded-Proto` (fall back to request scheme) and `X-Forwarded-Host` (fall back to `Host`), produce `<scheme>://<host>/enable-banking-callback`
- [x] 5.4 Implement `startOnboarding(email, callingUserSessionId)` — generate random `state` token; persist onboarding context (email, status=`PENDING`) bound to `callingUserSessionId`; derive the redirect URL from the calling request's forwarded headers; call `ControlPlaneClient.getOobConfirmationCode` with `continueUrl` = `<derived-redirect-url>?state=<token>`; return the `state` token AND the derived redirect URL (so the SPA can display it at the EmailEntry step as informational text)
- [x] 5.5 Implement `GET /enable-banking-callback` route (unauthenticated) — validate `state` against persisted contexts; on valid `state`, store `oobCode` on the context, set status=`CALLBACK_RECEIVED`, and SERVE THE SPA BUNDLE (per design D14) so the SPA renders a styled `CallbackScreen` "return to your original BankTeller tab" screen; on invalid `state` or missing `oobCode`, serve the SPA bundle so the SPA can render a styled error screen, without storing anything. The oobCode capture MUST happen server-side synchronously BEFORE the SPA bundle is served (the SPA does not relay the oobCode to the server via a separate API call — the server already has it from the GET request). The route handler SHALL NOT serve inline-HTML+CSS response strings; it serves the SPA bundle (the same `index.html` the foundation's catch-all serves for unknown paths).
- [x] 5.6 Implement `completeOnboarding(state, callingUserSessionId, environment, redirectUrl, productionFieldOverrides?)` — validate the `state` belongs to `callingUserSessionId` (return 403 on mismatch — multi-user future-proofing); validate context status is `CALLBACK_RECEIVED` (error if `PENDING`/not found); call `emailLinkSignin` to get `idToken`; for PRODUCTION environment, auto-derive the `description` (BankTeller default), `gdpr_email` (user's entered EB email), `privacy_url` (`<redirect-url-host>/privacy`), `terms_url` (`<redirect-url-host>/terms`) per design D13, applying any overrides from the request body; call `KeyPairGenerator`; call `ControlPlaneClient.registerApplication` with `idToken`, cert, environment, application name, the user-confirmed `redirectUrl`, and (for PRODUCTION) the derived description/gdpr_email/privacy_url/terms_url; persist `application_id` + private key + `redirectUrl` in `system_config`; call `verifyApplication` to check `active`; set status=`COMPLETED`; return success/failure with `active` status; on any step failure, do not persist credentials, set status=`FAILED`
- [x] 5.7 Implement `GET /api/onboarding/enable-banking/redirect-url` route (authenticated) — returns the derived redirect URL for the SPA to display in the RegistrationReview step as a pre-filled editable field
- [x] 5.8 Implement `POST /api/onboarding/enable-banking/start` route (authenticated) — accepts ONLY email (no environment, no redirect URL, no production fields — all deferred to the completion step per design D13/D8 reorder); validates email format; calls `startOnboarding` with the calling session ID; returns the `state` token AND derived redirect URL in the response
- [x] 5.9 Implement `GET /api/onboarding/enable-banking/wait?state=<token>` route (authenticated) — validates the `state` belongs to the calling user (403 otherwise); returns `{"status":"pending"}` if context status is `PENDING`, or `{"status":"complete"}` if `CALLBACK_RECEIVED`
- [x] 5.10 Implement `POST /api/onboarding/enable-banking/complete` route (authenticated) — accepts `state` token, `environment`, `redirectUrl`, and optional `productionFieldOverrides` (for PRODUCTION) in the body; calls `completeOnboarding` with these and the calling session ID; handles state-not-found, state-belongs-to-other-user, callback-not-yet-received, GIT-login-failed, registration-failed, verification-failed error cases with clear messages
- [x] 5.11 Implement `GET /api/onboarding/status` route (authenticated) — returns `OnboardingService.getStatus()` result
- [x] 5.12 Register `/api/onboarding/*` routes under the existing session-validation middleware; register `/enable-banking-callback` as an unauthenticated public route
- [x] 5.13 REMOVE the dedicated `/privacy` and `/terms` Ktor route handlers (per design D14). These paths are now served by the SPA: the foundation's existing catch-all SPA-bundle handler serves the bundle for these paths, and the SPA's public-route early-return (see task 7.10) renders the corresponding `PrivacyScreen` / `TermsScreen` composable. No dedicated Ktor route handler SHALL exist for `/privacy` or `/terms` after this change.
