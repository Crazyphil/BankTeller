## Context

The SPA is a Compose-WASM single-route app: the entire wizard position lives in `AppViewModel` memory, there is no URL router, so every refresh is a cold boot that re-derives routing from `GET /api/onboarding/status` + `GET /api/onboarding/state`. The login gate (`AppViewModel.checkOnboardingStatus`) infers only *completed* progress (whitelist, `eb_sessions`), so "linking started but not completed" is invisible: a refresh mid-linking routes to ActivationGuide ("Complete bank setup") because the EB app is still `inactiveNeverLinked` until the first link completes. Refresh mid-authorization resumes only coarsely (bank-list resume card). The session cookie is slim by design (identity + one-shot auth-failure diagnostics), with `ignoreUnknownKeys = true` for forward compatibility. The handle-authorization-failure change (archived) already added cold-entry AuthProgress machinery (failure display, retry, display-before-clear) that this change reuses. The archived `deleted-app-detection` change replaced the `active == false` + `enable_banking_previously_active` gate logic with control-plane application lifecycle states (`deleted` / `inactiveNeverLinked` / `inactiveButLinked` / `active` per the `eb-application-status` capability).

**Architectural principle (user-directed, governs this change):** *Whether* onboarding takes place at all — wizard vs. Dashboard vs. re-registration — is exclusively a server concern, decided from EB application state, the whitelist, and `eb_sessions`. The session contributes only *where in the wizard* the user is standing, which the server genuinely cannot infer from EB state. The goal is **navigational stability**, not an override of existing logic: pressing F5 (analogous to Android destroying and restoring an activity — which Compose Web cannot do, since F5 tears down the whole WASM heap and `rememberSaveable` does not survive a page reload) must show the user what they saw before, not direct them to a different corner of the app. Consequently the routing decision is **resolved server-side in one place** — the client must not re-create the server's checks: no client-side whether-onboarding logic exists under this change.

## Goals / Non-Goals

**Goals:**
- F5 within a session restores the exact onboarding screen (BankSelection / LinkingProgress resume mode / AuthProgress) with the in-flight bank data — navigational stability, nothing else.
- The whether-onboarding decision stays entirely server-side: the routing ladder is resolved by the server into a single `route` field; the SPA gate consumes it without re-deriving anything.
- Server-side inference remains the fallback for a new session (re-login): closest-possible point, never a blank start.
- View position is additional fine-grained flow-control data, never progress authority — a stale stage can never fabricate progress.
- Re-surface the AuthProgress failure-state retry ("Continue to your bank"): with `stage_bank` stored at `POST /api/auth`, the attempted bank triple (including `psu_type`) is known on cold entry, so the direct retry is offered whenever it is — closing handle-authorization-failure's transitional gap.
- Selecting an already-linked bank from the plain bank list continues directly to authorization (skips LinkingProgress), derived from server-side state (the whitelist) — not from cookie data.
- No new endpoints, no extra round trips: stage writes piggyback on existing touchpoint calls (`POST /api/link-accounts`, `POST /api/auth`, cancel-linking, callback success).

**Non-Goals:**
- URL/hash routing (a client-architecture change; the cookie approach covers the same-session case with far less surface).
- Persisting view position across sessions (re-login intentionally falls back to inference — the cookie dies with the session by design).
- Persisting any other wizard state (email entry, registration review, bank-list scroll, form fields).
- Dashboard-driven re-linking flows (future change).

## Decisions

**D1 — Cookie, not URL routing.** Alternatives: (a) URL/hash routing — survives cookie loss, shareable links, but requires a router architecture Compose-WASM doesn't provide, deep-links into mid-wizard screens for unauthenticated users, and per-screen URL mapping across 8 steps. (b) Server DB table — durable across sessions, but violates the slim-session design philosophy, adds a table + cleanup semantics for ephemeral data, and the user's model is explicitly "within a session: exact point; new session: closest-possible". The cookie is written at server touchpoints that already exist, costs ~100 bytes, and dies with the session — exactly the required lifetime.

**D2 — Stage written server-side at touchpoints, not client-side per navigation.** The SPA does not PATCH its view position on every step change (chatty, racy with multiple tabs). Instead the meaningful "user is now committed to this screen" moments are already server calls: `POST /api/link-accounts` success → `linking_progress`; `POST /api/auth` success → `auth_progress`; `POST /api/onboarding/cancel-linking` → `bank_selection` (the user deliberately returned to the bank list — recording it keeps F5 stable through the cancel path too; the bank triple is cleared, no bank is in flight). Two further UI actions fire the cancel-linking touchpoint **fire-and-forget** to persist the same deliberate-full-list signal: the ActivationGuide "start bank setup" button and the resume-card dismissal (`dismissResumeCard` — previously client-only, so a dismissed card reappeared after F5; the fire-and-forget POST persists the `bank_selection` stage, and the stage suppresses the card on restore). Clearing: auth-callback success, application (re-)registration via the onboarding completion endpoint (a stored position refers to the defunct application's flow — same rationale as the authorization-failure diagnostics fields cleared there), login (fresh cookie). This makes the stage a byproduct of real transitions, not a tracked mirror of client state.

**D3 — Route resolved server-side (single decision point); activation-first order preserved.** The full routing ladder is evaluated by a **pure server-side route resolver** consumed by `GET /api/onboarding/state`, which reports the outcome as a single `route` field. The ladder (first match wins): `registration_in_progress` (volatile in-memory marker — see D10) → `registration_progress`; `requires_relogin` → `email_entry`; application `deleted` → `registration_review`; `inactiveNeverLinked` → `activation_guide` **unless a stored stage is honored**; stage branch (consumed only when `auth_completed == false`): `auth_progress` (requires `linking_completed == true`) → `auth_progress`, `linking_progress` → `linking_progress`; at least one `eb_sessions` row → `dashboard`; `inactiveButLinked` best-effort continuation; `auth_failed` → `auth_progress` (failure display); whitelist non-empty → `bank_selection` (resume card shown when `selected_bank` is present — a display concern, not a route); else → `bank_selection`. The SPA gate collapses to a **dumb switch over `route`** — no client-side whether-onboarding checks exist; the client cannot drift from the server's logic (the user's explicit principle: whether onboarding takes place is a server concern; the session only refines where in the wizard the user stands). Deliberate properties: (1) **Activation-first:** the `inactiveNeverLinked` branch keeps its baseline position above the `eb_sessions`/Dashboard check — an inactive application with no linked accounts routes to `activation_guide` even for a previously-authorized user (EB returns an empty whitelist for inactive apps, so such a user derives `inactiveNeverLinked`; routing them to the Dashboard would prematurely abandon onboarding on dead sessions — onboarding is not complete until the application works). The only escape from ActivationGuide mid-flow is a stored stage (the reported bug: mid-linking the app is still `inactiveNeverLinked`, and the stored stage must win). (2) **`auth_completed == false` guard on stage consumption:** a stale stage (e.g. authorization completed in another tab) must be ignored rather than override real progress. (3) `linking_progress` is honored even when `linking_completed == true` (user completed an earlier link, then explicitly started a new one); `auth_progress` with `linking_completed == false` is inconsistent and ignored; a stage with a missing/blank bank triple is treated as no stage (`bank_selection` carries no triple by design and is always consumable). The resolver is a pure function over (application state, whitelist derivation, `eb_sessions`, session stage) — hermetically testable in fast JVM server tests; the gate tests move out of the slow browser-container suite. The state endpoint re-exports `app_state` and `pending_action` (from the same cached `OnboardingService.getStatus()` derivation the resolver consumes — the 30 s status cache) so presentation-level concerns (the `inactiveButLinked` and pending-action notes) need no client-side routing logic; the SPA gate no longer calls `GET /api/onboarding/status` (RegistrationReview pre-population uses the separate registration-info endpoint and is unaffected). (Baseline note: the ladder's application-state branches follow the `deleted-app-detection` change's lifecycle model — `deleted` / `inactiveNeverLinked` / `inactiveButLinked` — replacing the retired `active == false` + `enable_banking_previously_active` logic.)

**D4 — `UserSession` fields: flat, nullable, default-null.** `onboardingStage: String? = null`, `stageAspspName: String? = null`, `stageAspspCountry: String? = null`, `stagePsuType: String? = null`. Flat fields (not a nested object) match the existing cookie style and the kotlinx.serialization JSON-in-cookie encoding; `ignoreUnknownKeys = true` keeps pre-change cookies decoding cleanly (defaults null). Stage values are the three literals `linking_progress` / `auth_progress` / `bank_selection` — no enum class in the cookie payload (serializer simplicity); the server maps them to resolved `route` values and the SPA maps `route` to `OnboardingStep` destinations. `bank_selection` carries no bank triple (no bank is in flight; the triple fields are cleared when it is written).

**D5 — State endpoint resolves the route; raw flags remain for presentation.** `GET /api/onboarding/state` gains `route` (the D3 resolver output), `app_state`, and `pending_action` (both from the cached `OnboardingService.getStatus()` derivation the resolver consumes). The endpoint is no longer a dumb reporter for routing — routing is resolved here, once, server-side. The raw flags (`auth_failed`, `auth_error_kind`, `authorization_id`, `selected_bank`, `onboarding_stage`, `stage_bank`, `linked_banks`, `app_state`, `pending_action`) remain in the response because presentation *within* the routed screen needs them (failure-display variant, retry psu_type, resume card, skip-linking, status notes) — but they no longer drive routing on the client. Rationale: single decision point, hermetically testable in `:server` tests; the SPA cannot re-create or drift from the server's checks.

**D6 — SPA restore mechanics reuse existing resume paths.** The gate switch consumes `route` and, for `linking_progress`/`auth_progress` routes, feeds `stage_bank` into the existing restore machinery — no routing logic, only presentation wiring. `linking_progress` → set `selectedBankFromState`-equivalent state from `stage_bank` (so `isResumeMode` is true → LinkingProgress resume-mode UI: "Account linking was started in a previous session…", "Re-open linking page" via `relinkAccount()`, "I've completed linking" via `checkLinkStatus()`). `auth_progress` → AuthProgress cold entry: set the bank fields so "Continue to your bank" works with the right bank; when `auth_failed` is also true, the existing failure display renders (display-before-clear preserved — the SPA never auto-POSTs /api/auth on cold entry). **Non-failure restore carve-out:** display-before-clear governs *automatic* attempts and the failure display; in the non-failure restore (`auth_failed == false`) there is no error to display first, and the cold-booted screen has no in-memory `authRedirectUrl` — so the "Continue to your bank" action initiates a fresh `POST /api/auth` with the stored bank triple *when clicked* (user-initiated, not auto-started). Without this, the restored screen would be a dead end (disabled button, back-detour only) and the flagship refresh scenario would restore an unusable view. The stage bank triple feeds the same `SelectedBank` shape the resume card uses. **Resume-card suppression on restore (found during manual testing of task 7.3):** the card's display condition is `selected_bank` present AND no stored `bank_selection` stage — the stage is written only by deliberate full-list decisions (cancel-linking, the ActivationGuide start button, a resume-card dismissal), so it is a reliable suppression signal requiring no new server state; a stored `bank_selection` restores the plain full list. The dismissal itself persists via the cancel-linking touchpoint fired fire-and-forget from `dismissResumeCard()` (previously client-only, so a dismissed card reappeared after F5). **Failure-retry correctness (resolves handle-authorization-failure's transitional F3 gap):** the `stage_bank` written at `POST /api/auth` carries the attempted `psu_type`, so the failure-state retry ("Continue to your bank") is offered with the *correct* account type — including `business`, which the whitelist-derived `selected_bank` cannot know (it carries no psu_type; the HAF change removed the `"personal"` hardcode and makes the direct retry conditional on knowing the type). The failure path is inherently intra-session (`auth_error` dies with the session, so `auth_failed` never fires after re-login), which is exactly the stage's lifetime. **Precise invariant:** whenever the failure display renders (route `auth_progress` with `auth_failed == true`), `stage_bank` is present. **Accepted suppression:** a stage written *after* a failed attempt (a successful `POST /api/link-accounts` overwriting the stage from another tab, or cancel-linking followed by a late error callback) intentionally suppresses the stale failure display — the stage branch outranks the `auth_failed` rung, and the next `POST /api/auth` clears `auth_error` per the one-shot semantics; the user abandoned that attempt.

**D7 — Failure semantics: leave the old stage untouched.** A failed `POST /api/link-accounts` / `POST /api/auth` does not clobber the stored stage (the user's view position still reflects where they are). Stage writes happen only on success, after the EB call returns.

**D8 — Already-linked banks skip LinkingProgress (server-derived, not cookie-derived).** The state endpoint additionally reports `linked_banks`: the full set of `{aspsp_name, aspsp_country}` pairs derived from the whitelist (the same server-side source the resume card uses — no new state, no cookie involvement). When the user selects a bank from the plain bank list and the selection matches a `linked_banks` entry (name ∧ country), the SPA routes directly to AuthProgress (the `continueResumeWithBank` path — the same skip the resume card already performs) instead of LinkingProgress; the user confirms the PSU type on the selected-bank card as usual. When the bank is not in `linked_banks`, or the whitelist fetch failed / the list is empty (unknown state), the existing link-first path is kept — never guess that a bank is linked. **Accepted limitation (psu-type blindness):** the whitelist carries no `psu_type`, so the match keys on `{name, country}` only — a bank linked for personal matches a business selection too. The skip only avoids a step; the subsequent authorization is a real consent flow re-derived server-side, and a type mismatch surfaces through the standard failure handling — never fabricated progress. Rationale: linking an already-linked bank is a no-op server-side (the whitelist entry exists; `POST /api/link-accounts` would succeed trivially), so the linking step adds only friction; the resume card has always skipped it for the same reason. This is a behavior change to the plain bank-list flow (previously always link-first, byte-identical back to pre-HAF behavior), surfaced by the implementation agent's review of handle-authorization-failure — it is server-state-derived by nature (the whitelist *is* the linked-bank truth), so it belongs in this change rather than a cookie-only mechanism. The stage is unaffected: `POST /api/auth` still writes `auth_progress` + `stage_bank` as usual. **Accepted refresh gap:** the skip-linking transition to the consent preview is a pure client-side navigation — no touchpoint fires, the stage stays `bank_selection` until "Continue to your bank" triggers `POST /api/auth`, so an F5 at the consent preview returns to the bank list (one click away). This is the pre-existing resume-card pattern and follows D2's philosophy (the stage is a byproduct of real transitions, never a mirror of client navigation); it is now more common (every skip-linking selection), accepted.

**D9 — Infer the registration environment from the control plane; sandbox auto-activation rung.** The control-plane application entry (the same `GET /api/applications` lookup the lifecycle state derives from, empirically confirmed to carry an `environment` field — `SANDBOX`/`PRODUCTION` — on every entry) is the source of truth for the registration environment. The derivation parses it alongside `active`/`whitelisted_accounts`/`pendingActionType` (same cached lookup, no extra round trip, no persistence: no `system_config` key is written or read — an earlier draft of this change persisted `enable_banking_environment` at the completion endpoint; the user's review rejected that as redundant derived state, and it was dropped). The resolver gains a rung: `active` ∧ parsed environment `SANDBOX` ∧ no `eb_sessions` row → `dashboard`. Placement is deliberate: BELOW the stage branch (a sandbox user with a stored `bank_selection` stage still lands on the bank list — the stage mechanism wins, no fight), BELOW `eb_sessions` (an authorized sandbox user routes to `dashboard` through the existing rung), and BELOW `auth_failed` (a sandbox user who deliberately linked a bank and failed an authorization still gets the failure display; `auth_failed` requires a non-empty whitelist, so a pure sandbox user can never hit it — the rung only covers the deliberate-linking corner). A missing/blank/unrecognized `environment` field, or a failed CP lookup (unknown application state), falls through conservatively — the resolver never guesses sandbox. **Accepted degradation:** during a CP outage a never-authorized sandbox user degrades to `bank_selection` instead of `dashboard` (consistent with the endpoint's conservative-degradation philosophy — never fabricate progress); an *authorized* sandbox user still routes to `dashboard` via the local `eb_sessions` rung, which has no EB dependency. This closes the sandbox cold-boot inconsistency (in-session flow closes the gate on `active == true`; the resolver now agrees) without weakening any existing rung.

**D10 — Registration-in-flight marker: volatile in-memory, not a session stage.** The completion endpoint's registration task runs for a few seconds; an F5 during the "Verifying…" step cold-boots the gate, and every ladder rung would mis-route back to the registration form — during fresh onboarding the refresh token is not yet persisted (the registration task persists it), so even `requires_relogin` fires; a confused user back at the form could re-submit and create a duplicate EB application (the reported hazard). The fix is a volatile in-memory marker in the service (set when the registration task starts, cleared in a `finally` block on every termination path — success, retryable failure, non-retryable failure, exception), exposed to the resolver as a **top rung above `requires_relogin`** resolving the new `registration_progress` route; the SPA restores the verifying UI and keeps polling, and when the task terminates the next poll resolves per the remaining rungs — the user's "second refresh routes correctly" becomes "the verifying screen re-routes itself". Deliberately NOT a session stage: the server *knows* the task is running (same JVM) — the cookie is only for what the server cannot know; the marker's lifetime is exactly the task's (it dies with the JVM, so a server restart mid-registration leaves no stale marker trapping the user on a verifying step for a task that no longer exists — unlike a cookie stage); it is inherently multi-tab consistent; and it enables an **API-level concurrent-call guard**: a second `POST /api/onboarding/complete` while the marker is set is rejected with a structured error, making duplicate registration impossible rather than merely unlikely via routing.

**D11 — Resume-card enrichment: one fetch, no global busy.** Found during manual testing (task 7.3 follow-up): on the resume-card path the ASPSP list was fetched **twice concurrently** — `enrichResumeSelection()` (card enrichment: logo, BIC, psu_types, status) and `BankSelectionStep`'s enter effect firing `loadAspsps()` because `aspspsState` was still `Loading` (its initial value). The second fetch sets `isLoading` → `LocalActionBusy` disables every `ActionButton` app-wide, so the Continue button stayed disabled for a visible moment *after* the user selected an account type (the domain condition is met synchronously; the busy flag is not). The fix: the resume-card path performs exactly **one** ASPSP fetch (in-flight guard so the step's enter effect does not refire), and that fetch **does not set `isLoading`** — a prefetch is not a user action; the action-busy capability scopes the busy state to requests triggered by action buttons, so a background prefetch must not gate the app's buttons. The card keeps its existing wait-zone presentation during the single fetch (`WaitingIndicator.Zone` while `Loading`), and Continue enables the instant a chip is selected. No visual vocabulary is added (an inline busy spinner inside the button was considered and rejected: after the single-fetch fix no legitimate user-visible wait remains on this screen). The plain full-list path keeps its existing fetch-on-enter behavior.

## Risks / Trade-offs

- [Sandbox cold-boot routing inconsistency (found during manual testing of this change; pre-existing, not a regression — the old flag-based gate had the same gap)] → in-session, a sandbox registration completes with `active == true` and the SPA closes the onboarding gate (sandbox apps auto-activate and skip account linking); on cold boot the resolver had no matching rung and fell through to `bank_selection`. Root cause: the registration environment was not derived anywhere, so the server could not distinguish "active sandbox app, onboarding complete" from "active production app, no bank linked yet". Fixed by D9: infer the environment from the control-plane application entry (no persistence) and add the sandbox rung below stage/`eb_sessions`/`auth_failed`.
- [Server restart mid-registration] → the volatile marker dies with the JVM; the next cold boot routes per whatever was actually persisted (nothing → the registration form again; the user may re-register). If the EB application was created server-side before the crash but the credentials were not persisted, a re-registration creates a second EB application — a pre-existing crash-window hazard unchanged by this change (the marker neither widens nor narrows it); accepted, since the alternative (a persisted marker) would trade a bounded duplicate risk for an unbounded stale-trap.
- [Dismissed resume card reappears after F5 (found during manual testing of task 7.3)] → the dismissal was client-only memory (`resumeCardDismissed`), and the card re-derived purely from `selected_bank` on restore — overriding the user's explicit "choose a different bank" intent. Fixed: `dismissResumeCard()` fires the cancel-linking touchpoint fire-and-forget (persisting the `bank_selection` stage), and the card's display condition gains "no stored `bank_selection` stage" — the stage is written only by deliberate full-list decisions, so it reliably suppresses the card on restore. Residual: a dismissal fired during a server outage is lost (fire-and-forget, no retry) — the card reappears after that refresh; the user re-dismisses; accepted (the card is a resume aid, never a lock).
- [Multi-tab drift: tab A mid-linking, tab B completes auth] → the stage branch's `auth_completed == false` consumption guard (D3) ignores the stale stage, so the gate never regresses an authorized user; the stage is silently dropped.
- [Multi-tab semantics are session-scoped, not tab-scoped] → the cookie holds one position per browser profile, last-writer-wins: tab B starting auth moves tab A's next refresh to AuthProgress; cancel-linking in tab B moves tab A's next refresh to the bank list (the user cancelled, deliberately — and the bank list is where they land, not a bounce to ActivationGuide). Accepted: cancel is an explicit user action, and the shared-jar property is also a benefit (callback success in any tab clears the stage for all tabs).
- [Stage survives application re-registration] → covered: the onboarding completion endpoint clears the stage + bank triple alongside the authorization-failure diagnostics fields (D2) — a stored position refers to the defunct application's flow and must not route the user past ActivationGuide into the new application's onboarding.
- [Cookie size growth (~100 bytes)] → still far below the 4 KB cookie limit; flat nullable fields keep the payload compact.
- [Stage staleness after EB-side state changes (e.g. whitelist entry removed externally)] → the stage only restores a *view*; every action from the restored screen re-validates against the server (`checkLinkStatus` polls the whitelist; auth retry goes through `POST /api/auth` which re-derives everything). Worst case the user sees a screen whose action fails with a structured error — never fabricated progress.
- [Archive-ordering dependency on deleted-app-detection] → RESOLVED: deleted-app-detection is implemented and archived (c965fca); this change's gate delta is written against that baseline (application lifecycle states `deleted` / `inactiveNeverLinked` / `inactiveButLinked`; `enable_banking_previously_active` retired) and carries its gate scenarios forward. The handle-authorization-failure dependency is resolved (archived at 60b144a).
- [Refresh mid-linking with `linking_completed == true` from an earlier bank] → honored by design (D3): the user explicitly started a new link; the LinkingProgress resume screen's "I've completed linking" poll disambiguates actual completion.
- [Stale `bank_selection` after EB-side deactivation without re-registration] → the user cancelled, then the app was deactivated and unlinked purely on the EB side (no re-registration, so the completion-endpoint clear never fires): the next cold boot honors `bank_selection` above `activation_guide` → bank list instead of ActivationGuide. Accepted: `bank_selection` is the least-progressive stage (no fabricated progress), the bank list is one client-side back-click from ActivationGuide, any link attempt re-validates server-side, and the `auth_completed == false` guard keeps it below `dashboard`. Not worth machinery for a manual-CP-action scenario.
- [Two-cache incoherence: app state from the 30 s status cache vs. whitelist from the 60 s whitelist cache] → the first successful link flips `appState` from `inactiveNeverLinked` to `inactiveButLinked`, but link-accounts historically invalidated only the whitelist cache — a stageless cold boot within the ~30 s window could resolve stale `inactiveNeverLinked` + fresh non-empty whitelist → `activation_guide` (the reported bug, narrow window). Mitigated: link-accounts success SHALL invalidate the application-status cache alongside the whitelist cache (the combined invalidation already exists for registration).
- [Skip-linking false positive: bank in `linked_banks` but its EB session is actually dead (removed externally)] → the skip only avoids a step; the subsequent `POST /api/auth` does NOT re-validate the whitelist (it never consults it — it looks up the ASPSP list and calls `startAuth`), so it succeeds and initiates a real, fresh consent flow at the bank. Nothing is fabricated — the user genuinely consents — and a data-plane failure surfaces later through the standard failure handling. The user can still reach LinkingProgress via "Choose a different bank" → re-select.
- [Skip-linking false negative: whitelist fetch failed → empty `linked_banks` → user re-links an already-linked bank] → the existing link-first path handles it (linking an already-linked bank succeeds trivially); worst case is the pre-change friction, never a wrong route.
- [CP entry missing/unrecognized `environment` field (schema drift in the undocumented CP API)] → the derivation exposes null and the sandbox rung does not fire — the resolver falls through to the whitelist rungs (`bank_selection`), the pre-change behavior. Never guessed; no persistence to go stale.
- [CP outage during a sandbox cold boot] → the application lookup fails → unknown state → the sandbox rung cannot fire → a never-authorized sandbox user degrades to `bank_selection` instead of `dashboard`. Accepted: consistent with the endpoint's conservative-degradation philosophy (never fabricate progress); an authorized sandbox user still routes to `dashboard` via the local `eb_sessions` rung (no EB dependency); the outage window is bounded by the 30 s status cache and self-heals on the next successful lookup.
- [Resume-card Continue-button delay after chip selection (found during manual testing of task 7.3)] → root cause: two concurrent ASPSP fetches on the resume path, the second setting the global busy flag that disables all `ActionButton`s (D11). Fixed by the single-fetch + no-busy rule. Residual: while the single fetch is in flight the card shows the wait zone (existing presentation) — the button cannot be interacted with before the card renders at all, which is the pre-existing, understood loading state, not a post-selection delay.

## Migration Plan

No data migration. Cookie compatibility is one-directional forward (old cookies decode with null stage fields → resolver falls to inference; new cookies on old code are ignored via `ignoreUnknownKeys`). The SPA's `route` consumption is additive: an old SPA against the new server simply ignores the field (raw flags still present); a new SPA against an old server falls back to the existing flag-based gate until deploy completes (single-container deployment makes this window negligible). The deleted-app-detection baseline is already archived (c965fca); deploy order is simply implement → ship. Rollback: revert; old code ignores the new cookie fields.

## Open Questions

None — the user's model (session-exact, inference-fallback) is fully specified; gate precedence confirmed against the reported bug repro.
