## 11. Resume-card single-fetch (Continue-button delay)

> Root cause: on the resume-card path the ASPSP list is fetched twice concurrently — `enrichResumeSelection()` (fetch A, no busy flag) and `BankSelectionStep`'s enter effect firing `loadAspsps()` because `aspspsState` is still `Loading` (fetch B, sets `isLoading` → `LocalActionBusy` disables every `ActionButton` app-wide). Fetch A renders the card while fetch B is still in flight, so Continue stays disabled for a visible moment after a chip is selected. Fix: one fetch on this path, and it must not set the global busy flag (a prefetch is not a user action; the action-busy spec scopes the busy state to requests triggered by action buttons).

- [x] 11.1 `AppViewModel.kt`: single-fetch the resume-card enrichment — route `enrichResumeSelection()` through the shared `loadAspsps()` path (or add an in-flight guard so the step's enter effect does not refire); the resume-path fetch SHALL NOT set `isLoading` (no global busy on a prefetch); card enrichment (logo, BIC, psu_types, status) still derives from the fetched list
- [x] 11.2 `OnboardingScreen.kt` `BankSelectionStep`: enter effect must not trigger a second concurrent fetch on the resume path (in-flight guard or equivalent); the plain full-list path keeps its existing fetch-on-enter behavior
- [x] 11.3 SPA tests (AppViewModelTest): resume-card restore fires exactly one ASPSP fetch; `isLoading` is never true on the resume-card path; Continue enables immediately once a psu_type chip is selected (no busy-state coupling)
- [x] 11.4 `./gradlew :app:web:containerWasmJsBrowserTest` green
- [x] 11.5 Manual: resume card → select account type → Continue enables instantly; no visible delay between chip selection and button activation
