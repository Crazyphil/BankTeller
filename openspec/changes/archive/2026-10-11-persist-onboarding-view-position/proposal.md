## Why

Refreshing the page mid-onboarding loses the user's position in the flow: a refresh on the linking page routes back to the "Complete bank setup" (ActivationGuide) screen instead of resuming the in-flight linking, while a refresh on the authorization page resumes only coarsely (bank-list resume card). Linking and authorization resume behave asymmetrically because "linking started" is not persisted anywhere — the login gate can only infer completed steps from the Enable Banking whitelist. Modern users expect F5 to preserve all non-form state; the SPA currently keeps the entire wizard position in memory with no URL routing.

## What Changes

- `UserSession` cookie gains an onboarding view-position record: the current onboarding stage (`linking_progress` | `auth_progress` | `bank_selection`) plus the in-flight bank triple (`aspsp_name`, `aspsp_country`, `psu_type`; no triple for `bank_selection`). It is written server-side at the existing transition touchpoints (`POST /api/link-accounts` → `linking_progress`, `POST /api/auth` → `auth_progress`, `POST /api/onboarding/cancel-linking` → `bank_selection`) and cleared on auth callback success, on application (re-)registration (the onboarding completion endpoint — a stored position refers to the defunct application's flow), and at login (fresh cookie).
- **The routing decision moves server-side.** `GET /api/onboarding/state` gains a resolved `route` field, produced by a pure server-side route resolver that consumes the control-plane application state, the whitelist derivation, the `eb_sessions` table, and the stored session stage — in the existing activation-first order (`requires_relogin` → `email_entry`; `deleted` → `registration_review`; `inactiveNeverLinked` → `activation_guide` unless a stored stage is honored; stage branch, consumed only when `auth_completed == false`; `eb_sessions` → `dashboard`; `inactiveButLinked` best-effort; `auth_failed` → `auth_progress`; whitelist → `bank_selection`). Whether onboarding takes place is exclusively a server concern; the session only refines where in the wizard the user stands.
- **The SPA gate collapses to a dumb switch over `route`** — no client-side whether-onboarding checks remain; the client cannot drift from the server's logic. The gate tests move from the slow browser-container suite to fast hermetic JVM server tests. The state endpoint also re-exports `app_state` so presentation-level concerns (the `inactiveButLinked` note) need no client-side routing logic.
- Navigational stability (the Android activity-restoration analogy): F5 within a session restores the exact screen with its data — LinkingProgress in resume mode, AuthProgress cold entry (with a working "Continue to your bank" action that initiates a fresh `POST /api/auth` with the stored bank triple when clicked — no in-memory authorization URL exists on cold boot), or the bank list after a deliberate cancel. A new session (re-login) falls back to server-side inference — closest-possible point, never a blank start.
- **Resume-card suppression (found during manual testing of task 7.3):** the bank-list resume card's display condition gains "no stored `bank_selection` stage" — the stage is written only by deliberate full-list decisions (cancel-linking, the ActivationGuide start button, a resume-card dismissal), so a refresh after any of them restores the plain full list instead of re-deriving the card from `selected_bank`. The dismissal itself persists: `dismissResumeCard()` fires the cancel-linking touchpoint fire-and-forget (previously client-only, so a dismissed card reappeared after F5, overriding the user's explicit "choose a different bank" intent). SPA-only change; the server already writes the right stage.
- Server-derived state (whitelist, `eb_sessions`) remains the sole authority for completed progress; the view position is additional fine-grained data for flow control within a session, never a replacement — a stale stage can never fabricate progress.
- The AuthProgress failure-state retry ("Continue to your bank") is re-surfaced: the handle-authorization-failure change deliberately hid it on cold entry because the attempted `psu_type` was unknown (the whitelist carries no psu_type; BankTeller never guesses between personal and business). With `stage_bank` stored at `POST /api/auth`, the attempted bank triple is known on cold entry, so the direct retry is offered whenever it is — and only hidden when it isn't (pre-change cookie with no stage).
- Selecting an **already-linked bank** from the plain bank list skips the LinkingProgress step and continues directly to AuthProgress: the state endpoint reports the full set of linked banks (`linked_banks`, derived from the whitelist — server-side state, not cookie data), and the SPA checks the selection against it. Only the resume-card path skipped linking before; now the plain list does too when the bank is already whitelisted. A bank not in `linked_banks` (or an empty/failed whitelist fetch) keeps the existing link-first path. Accepted limitation: the whitelist carries no `psu_type`, so the match keys on `{name, country}` — a bank linked for one account type matches a selection of the other type too; the skip only avoids a step and the subsequent authorization is a real consent flow, so this never fabricates progress.
- No new endpoints; stage writes piggyback on existing calls, so no extra round trips. Note: with the gate consuming `route` from the state endpoint, `GET /api/onboarding/status` loses its last SPA caller — the endpoint stays (out of scope) but is flagged for a future cleanup change.
- **Sandbox cold-boot routing fix (pre-existing bug surfaced by this change's F5 testing):** the registration environment is inferred from the control-plane application entry (its `environment` field — `SANDBOX` | `PRODUCTION` — parsed alongside the lifecycle state in the same cached lookup, no persistence, no extra round trip), and the resolver gains a sandbox auto-activation rung (`active` + environment `SANDBOX` + no `eb_sessions` row → `dashboard`) — a sandbox registration completes without account linking (apps auto-activate), and the cold-boot resolver now agrees with the in-session flow instead of bouncing a sandbox user to the bank list. The rung sits below the stage branch (a stored `bank_selection` still wins), below `eb_sessions`, and below `auth_failed`; a missing/unrecognized environment field or a failed CP lookup falls through conservatively (never guessed).
- **Registration-in-flight marker (F5 during "Verifying…"):** the completion endpoint's registration task runs for a few seconds; an F5 during that window cold-boots the gate back to the registration form (during fresh onboarding the refresh token is not yet persisted, so even `requires_relogin` fires) — a confused user could re-submit and create a duplicate EB application. The endpoint maintains a volatile in-memory `registration_in_progress` marker (set at task start, cleared in a `finally` on every termination path, never persisted — it dies with the JVM, so a server restart leaves no stale trap), exposed to the resolver as a top rung above `requires_relogin` resolving the new `registration_progress` route: the SPA restores the verifying UI and keeps polling, re-routing itself as soon as the task terminates. While the marker is set, a second `POST /api/onboarding/complete` call is rejected with a structured error — the duplicate-registration hazard is eliminated at the API level, not just via routing. Deliberately not a session stage: the server knows the task is running (same JVM); the cookie is only for what the server cannot know.
- **Resume-card single-fetch (Continue-button delay, found during manual testing of task 7.3):** on the resume-card path the ASPSP list was fetched twice concurrently, and the second fetch set the global busy flag that disables every action button app-wide — so Continue stayed disabled for a visible moment after the user selected an account type. The resume path now performs exactly one fetch, and it does not set the busy flag (a prefetch is not a user action; the action-busy capability scopes the busy state to requests triggered by action buttons). Continue enables the instant an account type is selected; no visual changes.

## Capabilities

### New Capabilities

- `onboarding-view-position`: Persisting the user's current onboarding view position (stage + in-flight bank) in the session cookie at existing server touchpoints, resolving the full onboarding route server-side (application state + whitelist + `eb_sessions` + session stage → a single `route` field on the onboarding state endpoint), and consuming it in the SPA as a dumb switch — restoring the exact screen on refresh within a session, with server-side inference as fallback for new sessions.

### Modified Capabilities

- `onboarding`: The login-gate requirement is restructured — the routing ladder is resolved server-side by the state endpoint's route resolver (activation-first order preserved, per the archived `deleted-app-detection` baseline) and the SPA consumes the resolved `route` without re-deriving anything; the state endpoint requirement gains the `route` / `app_state` / `onboarding_stage` / `stage_bank` / `linked_banks` response fields; the auth-initiation and account-linking route requirements gain the stage-write behavior; the cancel-linking requirement gains the `bank_selection` stage write; the completion-endpoint requirement gains the volatile registration-in-flight marker (top resolver rung `registration_progress` + concurrent-call guard + view-position clear on re-registration); the SPA AuthProgress requirement re-surfaces the failure-state direct retry (offered whenever `stage_bank` is stored); the SPA BankSelection requirement gains the already-linked skip-linking routing. The ActivationGuide gate scenario stays authoritative for users with no stored stage (fresh registration / new session).
- `eb-application-status`: The application lifecycle state model requirement gains the `environment` field — parsed from the matched control-plane application entry alongside `active`/`whitelisted_accounts`/`pendingActionType` (same cached lookup, no persistence, no extra round trip) and exposed to the route resolver's sandbox auto-activation rung; missing/blank/unrecognized values resolve to null and are never guessed as sandbox.
