# Design: server-side-onboarding-state

## Context

Onboarding progress (psuIdHash, selected bank, ebSessionId, accountsJson) lives in the HMAC-signed client-side session cookie. Login replaces the cookie, so re-login / expiry / volume rebuild destroys progress and the SPA misroutes. This change moves derivation server-side, keeping the cookie as identity-only.

Verified EB API constraints (from reference docs):
- Control-plane `GET /api/applications` (undocumented, used by our client today) returns entries with `active` and `whitelisted_accounts` (fields: `created`, `aspsp{name, country}`).
- Data-plane `GET /sessions/{id}` returns `status` (INVALID / PENDING_AUTHORIZATION / RETURNED_FROM_BANK / AUTHORIZED / EXPIRED / CLOSED / REVOKED / CANCELLED) and `accounts` (uids only, no IBAN).
- There is **no** list-sessions endpoint → the `session_id` from `POST /sessions` must be persisted server-side; it cannot be rediscovered.
- Expired session → HTTP 401 with error `EXPIRED_SESSION`; unknown session → 404.
- Account `uid`s are session-scoped; VISION.md §5.1 proposes `identification_hash` as the stable cross-session account key. This change deliberately deviates: once IBAN is stored at auth time it serves the same purpose, so cross-session matching is done by IBAN.

## Decisions

- **D1 — Cookie = identity only.** `UserSession` keeps `username` and `authError` (one-shot carrier for the callback-error → SPA handoff; cleared on next auth attempt, as today). All progress fields are removed. Session re-issue on login becomes a plain fresh cookie; the earlier preserve-on-login workaround becomes unnecessary (it is harmless either way, but the reason for it disappears). Pin the session serializer to kotlinx.serialization `Json { ignoreUnknownKeys = true }` so old cookies containing the removed fields decode cleanly to `UserSession` defaults without forcing logout.
- **D2 — Real domain storage for authorized sessions.** New SQLDelight tables in `:core` (`core/src/commonMain/sqldelight/it/kapfer/bankteller/database/`):
  - `eb_sessions(id INTEGER PK, session_id TEXT NOT NULL, aspsp_name TEXT, aspsp_country TEXT, psu_type TEXT, created_at INTEGER NOT NULL)` — one row per authorized data-plane session. A user may authorize multiple banks over time; re-authorization after expiry creates a **new row** (no upsert on `session_id`).
  - `accounts(id INTEGER PK, session_id INTEGER NOT NULL REFERENCES eb_sessions(id), iban TEXT, uid TEXT, currency TEXT, name TEXT)` — one row per account from the `POST /sessions` response.
  The auth callback persists these rows on `authorizeSession` success, parsing the `AuthorizeSessionResult.Ok` payload into **structured fields** (no raw JSON blob). IBAN/uid are not re-derivable for an account via list endpoints, so they must be captured at auth time. Cross-session account matching is done by **IBAN** — a deliberate deviation from VISION.md §5.1's `identification_hash`, which serves the same purpose once IBAN is stored. SQLDelight is the migration framework: this change adds versioned `.sqm` migrations in `:core` for the two new tables, following the existing conventions (reuse the existing SQLDelight query pattern from `SystemConfig.sq`). **Runtime migration is required:** `DatabaseFactory.init()` must call `Schema.migrate(driver)` for versioning — existing databases with the old schema cannot just `create` (the current `DatabaseFactory.init()` only runs `Schema.create` inside an "already exists" swallow). Migration upgrades the existing `/data/bankteller.db` in place without data loss.
  **Re-authorization (same bank, new consent):** two phases.
  - **Phase 1 — external gate, NOT transactional:** `authorizeSession(code)` runs against Enable Banking and touches nothing in the DB. On failure no DB rows are modified — the old `eb_sessions` row and its account rows stay intact and a retry is unaffected. This is the actual "must not strand the user" property: the DB is only ever written once a new payload exists.
  - **Phase 2 — atomic merge:** once the new payload exists, ALL database steps run inside ONE SQLDelight transaction: insert the new `eb_sessions` row; for each account in the new response, match by IBAN against existing account rows — on match update the mutable fields (`uid`, `name`, `currency`) and re-point `session_id` to the new session; on no match insert a new account row; matching is by **IBAN only** — IBANs are globally unique (the bank and country are encoded in the IBAN itself), so an IBAN match can only ever hit the same real-world account and a cross-bank collision is impossible by construction; an account with no IBAN (e.g. a card `maskedPan` or `bban`/`msisdn` identification) is inserted as a new row without attempting a match, a documented residual limitation: such rows may duplicate across re-auth (orphans from the old session are still cleaned by the session-deletion step, which is unaffected); delete the previous `eb_sessions` row(s) belonging to the SAME bank — matched by `aspsp_name` + `aspsp_country` equality with the new row — and their orphaned account rows (accounts of the old session that did not reappear — e.g. the user de-selected accounts at the bank). Rows for other banks are never touched. Commit or roll back as a unit — no partial merge states possible. **Idempotency:** if `authorizeSession` returns a `session_id` already present in `eb_sessions` (duplicate callback — the single-use code already redeemed), treat it as success since the existing row already represents this consent; do not duplicate. Single-flight the merge — the `UNIQUE` constraint on `session_id` is the guard: a concurrent duplicate insert fails on the constraint, so callbacks cannot interleave partial merges.
- **D3 — Derive, don't store, linking state.** `linking_completed` = control-plane `getApplication` returns `active == true` AND `whitelisted_accounts` non-empty. `selected_bank` = name/country info from the newest whitelisted entry (order whitelist entries by their `created` field descending and take the newest; if `created` is null/empty, fall back to the last list entry; psuType falls back to "personal"; the whitelist entry has no psuType). No `psuIdHash` involvement. `whitelisted_accounts` exists only for active applications with ≥ 1 linked account; an application without completed linking yields no whitelist, so `selected_bank` stays null and routing goes to BankSelection. **Resume routing (NOT the login gate):** the `selected_bank` pre-selection aid is used only when the user explicitly restarts linking from within a session — mid-wizard re-entry (a fresh tab/reload during linking with a linked-but-incomplete auth: whitelist entry exists, no `eb_sessions` row for the current flow) or a future dashboard-driven add-account flow. In those cases route to the **resume card** — a prominent single-bank card for the stored bank (headline typography, logo + BIC from `/api/aspsps` enrichment), with the `psu_type` selector directly on the card (Personal/Business segmented control, defaulting to unselected, helper text, inline validation when left unconfirmed) and the primary "Continue with [Bank]" action in the wizard footer's forward slot (enabled only once `psu_type` is chosen); **"Continue with [Bank]" transitions to the AuthProgress consent preview — NOT directly to the authorization redirect** — the user gets the same explanation of what authorization will do as a user arriving from account linking, so they are never sent to the bank's domain without context; the bank SCA redirect fires only from AuthProgress's "Continue to your bank". LinkingProgress is skipped in this resume (linking is already completed — the whitelist entry exists). Below the card a quiet "Choose a different bank" affordance (QuietButton) reveals the full searchable list. Rationale (designer-reviewed): a pre-selected card buried in the ~2700-entry list is invisible, and a pre-filtered list reads like a broken search — the resume card makes the actual purpose of the stop (psu_type confirmation) the visual centerpiece. The resume card is a resume aid, never a lock; choosing a different bank abandons the card and shows the standard list. AuthProgress resumes only when a session row exists at least once. This resume route is also used by the login gate in exactly one case — linked-but-never-authorized (see D4).
- **D4 — Onboarding gate (revised): whitelist-driven, no live session check.** Routing on login is decided from the control-plane whitelist + the `eb_sessions` table. The gate is exactly (conditions are evaluated in the listed order; the first match wins — the inactive check dominates all whitelist/`eb_sessions` checks):
  - EB application no longer `active` (via the status endpoint's application verification — the data-plane `verifyApplication` call — reporting `active == false`; the old auto-reset heuristic in `OnboardingService.getStatus` that wiped credentials is removed by this change — see D10), disambiguated via the `enable_banking_previously_active` marker (set when the status endpoint's verification reports `active == true`; blanked by credentials reset and re-registration): a **previously-active** application (deleted/deactivated from the EB control panel) → **RegistrationReview** (review + resubmit registration), even if previously completed; a **never-active** application (fresh PRODUCTION registration pending activation) → **ActivationGuide** (the standard post-registration step). With the refreshToken still present, the user's EB email/refreshToken are **not re-entered** — credentials are preserved and preloaded so the review step can submit directly. The EB registration email is persisted at onboarding completion (`enable_banking_email` in `system_config`) and pre-fills the RegistrationReview step; when it was never stored (pre-feature volume), the field is empty and the user enters it once (the private key is never re-entered either way). `requires_relogin` (refresh token absent) outranks this branch — a user without a refresh token goes to EmailEntry regardless. **Only** this condition revokes completed onboarding.
  - Whitelist non-empty AND at least one `eb_sessions` row (authorized at least once ever) → **Dashboard** — the normal case. Expired/revoked consent does **not** regress to onboarding: `eb_sessions` rows persist across later consent expiry (they are only deleted on same-bank re-authorization), so a previously-authorized user still lands on Dashboard; the dashboard will show re-auth affordances (future change).
  - Whitelist non-empty but NO `eb_sessions` row (linked but never authorized) → **Onboarding**, resuming at the **resume card** for the stored bank (the same mechanics as mid-wizard resume: prominent single-bank card from `selected_bank` with `/api/aspsps` catalog enrichment, `psu_type` confirmed explicitly on the card, "Continue with [Bank]" primary action transitioning to the AuthProgress consent preview — not directly to the authorization redirect —, quiet "Choose a different bank" affordance revealing the full list) — deliberate decision: onboarding counts as complete only after the first successful authorization; the wizard's job is a meaningful dashboard, which requires at least one authorized session.
  - Whitelist empty → **Onboarding**, starting at the **BankSelection** step (no whitelist entry → no `selected_bank`).
  The `selected_bank` pre-selection aid is part of the login gate in exactly one case — the linked-but-never-authorized resume above; otherwise it applies only when the user explicitly restarts linking from within a session (mid-wizard re-entry or a future dashboard-driven add-account flow). It is never a navigation lock. Consequently the login-time live `GET /sessions/{id}` status check is **unnecessary and dropped** from the gate. The gate runs only at app load / fresh login via `checkOnboardingStatus`; mid-wizard navigation within a session is purely client-side (`AppViewModel.onboardingStep`) and is never persisted server-side. The state endpoint's `auth_completed` derives from the `eb_sessions` table (true if at least one row exists).
- **D5 — Scope boundary: the bank-setup wizard is one reusable unit.** The three steps BankSelection → Linking → Authorization are treated as a single unit. Future changes will re-enter the wizard from the dashboard when a link is removed or a session expired (possibly with "you're refreshing an existing account" copy). **Not part of this change** — recorded here as future direction only.
- **D6 — Navigation is never locked.** Users can always return to BankSelection, even mid-linking. The cancel-linking path keeps working and becomes trivially simple: it clears nothing but the one-shot `authError`; SPA-side navigation is always allowed. `selected_bank` derivation from the whitelist is a resume aid only, never a navigation lock.
- **D7 — Bounded API traffic via a shared TTL cache.** Introduce a small reusable TTL-cache abstraction (e.g. `TtlCache<K, V>` / memoize-with-ttl helper) used for BOTH the existing status cache and the new whitelisted-accounts cache (TTL 60 s), replacing the ad-hoc `STATUS_CACHE_TTL_MS = 30_000` copy pattern in `OnboardingService`; invalidated on link-accounts POST. The whitelist cache is used ONLY by the polled `/api/onboarding/state` derivation; `/api/onboarding/link-status` (user clicked "I've completed linking") MUST bypass/invalidate the cache and fetch fresh, then prime the cache with the fresh result on a match so downstream `/state` calls stay consistent. No session-status cache is needed since the gate performs no live session check. Cache negative results too (consistent with existing behavior) but keep the TTL short so user actions converge quickly.
- **D8 — Failure posture.** If the control-plane call fails transiently (network/5xx) while deriving, the server-side derivation MUST NOT error with 5xx — return the conservative defaults (no progress) without SPA-visible degradation machinery (that's a future change). Never throw 500 from `/api/onboarding/state` — the SPA needs this endpoint to always answer. `auth_completed` derives from the local `eb_sessions` table (no EB dependency) and remains authoritative: a user with at least one `eb_sessions` row still routes to Dashboard at login even when the whitelist fetch fails; the conservative no-progress degradation applies only to users without an `eb_sessions` row.
- **D9 — link-status endpoint simplification.** `GET /api/onboarding/link-status` drops the cookie-based `psuIdHash != null` test and answers purely from a **fresh** control-plane whitelist fetch (bypassing/invalidating the shared 60 s cache — the user just clicked "I've completed linking" — then priming the cache with the fresh result on a match; matching by aspsp name/country when a bank was in-flight this session — for the active "just linked?" polling case we still compare against the bank the user selected this session *in the SPA* and posts nothing extra; the endpoint semantics simplify to "does a whitelist entry exist (optionally matching name/country params)"). Being user-triggered (one click), its cache bypass is acceptable load — the rate-limit/no-hammering guarantee applies to the polled `/state` path, not to per-click link-status calls.
- **D10 — Remove the auto-reset landmine.** `OnboardingService.getStatus()` currently calls `resetCredentials()` (wiping application id, private key, refresh token) when a previously-active app reports `active == false` — this contradicts the new gate, which intentionally routes inactive → onboarding **while preserving the registration**. Remove the `resetCredentials()` call from `getStatus()`. An inactive app routes to onboarding with credentials still present, so the user re-registers or fixes the app **without re-entering the private key**. Detection = "app is inactive"; recovery = re-register.
- **D11 — Single-user scope (deliberate).** This app is single-user by design (VISION.md §2/§4.3): the `eb_sessions`/`accounts` tables carry **no `username` column** and there is no per-user filtering. Any future multi-user work must redesign this (add ownership columns + scoping); out of scope here.
- **D12 — One-time legacy-cookie import on first login.** After this change ships, existing volumes have an empty `eb_sessions` table while old cookies still carry the removed progress fields (`ebSessionId`, `accountsJson`, `psuIdHash`, `aspsp*`, `psuType`). Without a migration, such users would be routed to BankSelection despite having authorized before. The **login handler** (`POST /api/login`) SHALL, on successful credential validation AND an incoming cookie that still deserializes with legacy fields (they decode because the serializer pins `Json { ignoreUnknownKeys = true }`; a `LegacySessionPayload` DTO mirrors the old `UserSession` shape) AND an empty `eb_sessions` table, import the legacy state: insert one `eb_sessions` row (`session_id` = `ebSessionId`, `aspsp_name`/`aspsp_country`/`psu_type` from the old fields) plus `accounts` rows parsed from `accountsJson` (IBAN-based; `uid`/`currency`/`name` mapped 1:1). The import runs inside the usual transaction semantics; any error is logged and login still succeeds (the import is best-effort, never a login blocker). The newly issued cookie is the slim identity-only one (legacy fields dropped). **Idempotent:** `eb_sessions` non-empty → no import — it only ever runs once per deployment. Placed in the login handler (not the callback) because it is the single guaranteed entry point for an existing user after upgrade, and it runs before the gate routes them. If the legacy cookie carries no `ebSessionId` (linked but never authorized pre-change), nothing is imported; the gate routes via the linked-but-never-authorized branch.

## Alternatives considered

- **Full DB row per onboarding state** (original sketched design): rejected — duplicates state the EB API already knows (linking); the EB API is authoritative for linking/whitelist state at any time, so it is derivable on demand. Only `session_id`/IBAN/uid are issued once and not listable later, so only those must be persisted.
- **Keep cookie fields + fix login to preserve them**: rejected — stale data lifetime equals cookie lifetime; multi-tab and expiry races remain.

## Risks

- Control-plane endpoint is undocumented; field shape could change. Mitigate by tolerant deserialization (already: `ignoreUnknownKeys`) and a logged-but-conservative fallback (D8).
- Whitelist-entry doesn't carry psuType or IBAN — resume can pre-fill bank name/country only; acceptable.
- Cross-session account matching relies on IBAN stability (deliberate deviation from VISION.md §5.1's `identification_hash`). Mitigate by matching on the normalized IBAN captured at auth time and documenting the deviation in the schema.
- Cache staleness ≤ 60 s after linking — user clicks "I've completed linking" → worst case one retry. Acceptable; invalidate on the completion-button server call path to eliminate even that.
- A linked-but-never-authorized user is pulled back into onboarding (bank-list resume) at each login until the first authorization succeeds — deliberate (D4); there is no "skip and use the dashboard" escape until `auth_completed` is true.

## Future direction (not in scope)

- Dashboard re-entry into the bank-setup wizard when a link is removed or a session expires, possibly with "you're refreshing an existing account" copy (D5).
- Dashboard health feature to surface expired/revoked consent with re-auth affordances; the data-plane session-status retrieval method will be designed as part of that change (D4).
