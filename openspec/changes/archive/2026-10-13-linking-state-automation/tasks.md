## 3. Linking-session-status poll endpoint

- [x] 3.1 Add `GET /api/onboarding/linking-session-status` (authenticated, session cookie required; 401 without) in `AccountLinkingRoutes.kt`: no stored sessionid, no stored base URL, or no stored stage → `{ "state": "unavailable" }` without contacting EB
- [x] 3.2 State mapping: `Ok` with any status value other than `AuthDone`/`Cancelled`/`Invalid` (including unknown values) → `waiting`; `Cancelled` → `cancelled`. `Invalid` and any `Error` (both kinds) are outranked by the whitelist — the authoritative "is the account linked" signal (design D5, dead-session rule): `Invalid` runs a fresh whitelist confirm first (stage's bank linked → `done`; not-linked → `failed` — the session is dead, no retry; whitelist unreachable → `unavailable`), and `Error` consults the cached whitelist snapshot (linked → `done`; otherwise → `unavailable`) without distinguishing the cause to the SPA. `AuthDone` → sticky in-memory marker keyed by sessionid (first-observed timestamp, next-due timestamp, result; top-level state like the whitelist cache, 15-minute TTL, clear-hook for tests): the first observation runs the whitelist confirmation check immediately (reuse the existing `fetchWhitelist(..., forceRefresh = true)` path from the link-status endpoint) matching the **stage's bank** (`aspsp_name` + `aspsp_country` from the stored view-position triple, mirroring link-status's filtered mode — a whitelist entry for a different bank does not confirm) → `done` on linked (sticky); not-linked or check failure (control-plane network errors included — they consume a retry, not `unavailable`) → `confirming` with retries on a backoff schedule (5s, 10s, 20s, 40s, capped at 40s) within a 2-minute budget from first observation (~6 attempts); a poll arriving before the next-due timestamp returns `confirming` without running a check; budget exhaustion → `unconfirmed` (sticky). While the marker is active the endpoint does NOT call the EB AIS endpoint at all — the marker is the session's state (robust against the tilisy session being cleaned up after `AuthDone`), and a SPA that misses a terminal response gets the sticky result on its next poll without re-running any whitelist fetch
- [x] 3.3 Log every observed status value at info level (including unknown values) for future terminal-state discovery; never log the sessionid
- [x] 3.4 Route tests: 401 without cookie; no-sessionid/no-base-URL → `unavailable` without EB call; non-terminal status → `waiting`; unknown status value → `waiting` (and logged); 200 with missing status field → `unavailable`; first `AuthDone` + whitelist linked for the stage's bank → `done`, and a second poll returns `done` from the marker without a new EB or whitelist call (sticky); `AuthDone` + not-linked → `confirming` with the next attempt scheduled per the backoff, and a poll before the next-due timestamp returns `confirming` without a new whitelist call; `AuthDone` + whitelist entry only for a different bank → `confirming` (not-linked); `AuthDone` + confirm check network failure → `confirming` (consumes a retry, NOT `unavailable`); budget exhaustion (2 minutes from first observation) → `unconfirmed` (sticky); while the marker is active the EB AIS endpoint is not called (e.g. an `INVALID_SESSION` tilisy response after `AuthDone` does not degrade to `unavailable`); `Cancelled` → `cancelled`; `Invalid` → `failed`; `INVALID_SESSION` and network failure without a marker → `unavailable`; the marker map is top-level server state that survives across `testApplication` instances — add a map-clear hook (mirroring `clearWhitelistCacheForTests()`) and clear it between tests; make the backoff schedule and budget injectable/overridable so the exhaustion test does not really wait 2 minutes
