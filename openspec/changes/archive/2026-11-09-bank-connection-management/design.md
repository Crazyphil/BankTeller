# Design: Bank Connection Management

## Context

BankTeller has one authenticated screen (the dashboard) and one bank-level action ("Add bank" in the metadata strip). Re-authorization exists and is reason-agnostic (dead consent, expiring consent, broadened filter — identical path, direct wizard entry at AuthProgress), but is only triggered by consent-dead/expired notices. There is no way to list connections, refresh a live bank's authorization, or remove a connection. Same-bank re-auth merge silently deletes orphaned accounts (accounts not in the new selection) — accepted under D22 of `add-account-overview`, but in tension with the user's retention principle. Multiple archived changes deferred the navigation component explicitly to "the bank-connection change"; the `ScreenShell` reserves a fixed `bottomBar` slot for it.

Research settled during exploration:

- **Enable Banking session revocation exists**: `DELETE /sessions/{session_id}` (JWT auth like all calls, 200 `{"message":"OK"}`, 404 possible). Spec verbatim: *"Delete session by session ID. PSU's bank consent will be closed automatically if possible"* — EB-side closure unconditional, bank-side consent closure **best-effort** (ASPSP-dependent). No `GET /sessions` list endpoint exists — our persisted session ID is the only handle to the consent. No Kotlin SDK (hand-rolled `EnableBankingClient.kt` gains `deleteSession`).
- **Compose Multiplatform 1.11.1 (wasmJs)**: `material3-window-size-class` stable; `ListDetailPaneScaffold` (material3-adaptive) stable on its own version train (1.3.0) but built for three-pane apps; `NavigationSuiteScaffold` **alpha-only** at the 1.11.x line (stable stops at 1.9.0).
- **Schema**: `eb_sessions` has `created_at` (add date exists) but **no BIC**; `accounts.session_id` is NOT NULL FK to `eb_sessions`; account matching at merge is by IBAN only (null-IBAN accounts always insert as new rows).

## Goals / Non-Goals

**Goals:**

- First real navigation: tab bar + Settings surface, establishing the settings pattern for future sections.
- Bank connections section: list with metadata, refresh-authorization affordance (every connected bank, regardless of consent state), remove flow (EB revocation + local cleanup).
- Abolish silent data deletion at re-auth merge; give the user the delete-vs-keep choice.
- Absorb the dashboard's "Add bank" into bank management.
- Zero-account guidance at the moment of truth (onboarding first connection), suggestive not gating.

**Non-Goals:**

- No per-bank detail-detail view (actions inline in the connections list).
- No transaction feature, no workflow/automation feature — the automation guard is specced as a principle only.
- No routing library; no `ListDetailPaneScaffold`; no alpha dependencies.
- No changes to the onboarding completion condition (`auth_completed` = ≥1 `eb_sessions` row; accounts not required).
- No proactive renewal nudge machinery beyond the connection list's `valid_until` display with the existing 7-day urgency threshold.

## Decisions

### D1: The intent principle (governing rule)

Data loss follows only explicit user choice. System failures — bank outages, dead consents, EB/bank-side errors — never delete data. Consequences: sync failures never delete (already true — upserts only); first successful sync after an outage never removes data (already true); re-auth never silently deletes (changed by D8 — the one prior violation); user-initiated remove deletes everything derived from the connection (D7). The principle is quoted in specs so future changes inherit it.

### D2: Navigation introduced now; chrome scope

A tab bar renders on top-level authenticated screens only (Dashboard, Settings; Workflows later). The wizard's mid-flow steps are conceptually a full-page overlay and stay chrome-free (consistent with its autonomous three-zone layout, D30 of `add-account-overview`); the wizard's initial-import step is NOT a bar-suppressing state (it renders confined in the dashboard's content zone with the bar visible — D17); login, onboarding gate, callback, and public/legal screens stay chrome-free. This honors the explicit deferral IOUs (`2026-08-06-onboarding-enable-banking` D6/design: "the navigation component stays deferred to the bank-connection change"). Navigation remains enum-based (`Screen` enum + `when`); no routing library.

### D3: Tab bar form — centered bottom bar, hand-rolled

Designer ruling (des-1): a **unified centered bottom bar** rendered in `ScreenShell`'s reserved `bottomBar` slot, bounded to the content max-width (720dp) — NOT a left navigation rail. Rationale: the layout is anchored to a centered reading column; a viewport-edge rail sits far from the reading focus and reads as SaaS console, not ledger; two tabs make a 100vh rail look deserted; horizontal space is precious for financial data. Styling per the ledger aesthetic: ~52dp height, transparent/`surface` container, borderless at rest (a crop-signal hairline on the top edge renders only while content scrolls beneath the bar, per the crop-signal principle later codified as DESIGN-LANGUAGE §6.1.4 — superseding this decision's original permanent-hairline styling), outlined Material icons, active tab = `primary` text + discrete 2dp brass hairline indicator beneath, inactive = `onSurfaceVariant` at 60%, Inter `labelSmall`. Implementation is hand-rolled (~30 lines: `NavigationBar`/`NavigationRail` semantics are trivial at this scale) — `NavigationSuiteScaffold` is alpha-only at CMP 1.11.1 and stock M3 pill styling fights the aesthetic anyway. Not reactive between bar/rail forms: one form, all viewports (the centered bar is viewport-agnostic because it is bounded to the content column, not the viewport).

### D4: Settings pattern — hand-rolled master-detail

Designer ruling: hand-rolled two-pane layout via `material3-window-size-class`, not stock `ListDetailPaneScaffold`. Rationale: the adaptive scaffold is engineered for three-pane apps with back-stack orchestration; BankTeller's settings have exactly two levels (static section list → one panel), and the scaffold fights the 720dp content container. Expanded (>768dp): `Row` — fixed ~200dp section nav column (1dp vertical hairline divider, `outline` 8%) + detail panel `weight(1f)`. Compact (≤768dp): list→drill — section list first, panel with an inline "← Settings" `QuietButton` back affordance. The section nav is the same fixed-anchor idea as the pinned wizard footer (D30): stable spatial structure, no layout-shifting navigation. The `ScreenShell` top-bar divider keys on the **active panel's** scroll offset in two-pane mode.

### D5: Bank connections section — list with inline actions, no detail-detail view

The section header carries the canonical "+ Connect bank" `ActionButton` (top-right) — the absorbed dashboard control. Each bank renders as an `OutlinedCard` (designer anatomy): header zone (40dp logo, name `titleMedium`, "country · PSU type" subtitle, consent-health badge right: healthy = quiet "Consent active · Valid for N days"; ≤7 days = brass "Consent expiring"; dead/expired = danger "Consent ended · Re-authorization required"); middle zone = informational read-only accounts list ("ACCOUNTS (N)" label, name, masked IBAN in mono, trailing balance in mono `tnum`), capped at 4 visible rows with a "Show N more accounts" expander; footer action strip (last-synced left; the per-bank actions right at the **Inline Text XS tier** — §6.1.1's 28dp dense tier with min-touch-size opt-out, never the standard 40dp buttons initially built: "Refresh authorization" = XS action button, explicit text + 14dp key glyph, never unlabeled, never a circular arrow; "Remove" = XS danger action, danger text + 14dp delete glyph — glyph aids scanning, danger text keeps the destructive anchor, the confirmation dialog is the gate. Final ruling after a three-way reconciliation: user pushback (40dp text buttons clunky) → designer reject of icon-only (always-visible labels, danger needs a text anchor, §6.1.2 reserves text for high-consequence actions) → user synthesis (icon + text at XS). The strip is bounded by the row-height invariant — a single quiet line, no meaningful screen-estate cost). Zero-account banks render an info box ("No accounts shared under this authorization") with actions still available. Kept-as-local-copy accounts render with a "Local copy" tag, stale balance in `onSurfaceVariant`, and an inline XS danger delete affordance. BIC and add-date display in the card (BIC nullable, degrades gracefully like `logo`/`valid_until`).

### D6: Refresh authorization — existing path, new trigger only

The per-bank "Refresh authorization" action enters the existing reason-agnostic re-auth path unchanged: wizard AuthProgress, bank pre-selected, `RE-AUTHORIZATION` flow context, brass `ACCOUNT SELECTION NOTICE` explainer. No new flow machinery — the affordance was the only missing piece. Naming discipline (glyph collision rule, per DESIGN-LANGUAGE §6.1.1/§6.1.2; §6.1.8.3 states the consequence for the connection card): the authorization refresh never renders unlabeled and never uses a circular-arrow glyph (reserved for balance sync — an unlabeled circular arrow reads as data synchronization); it carries explicit text + a key glyph, visible without hover. The balance refresh stays icon-only on the dashboard (refreshing the authorization renews the EB session; refreshing balances is a data sync — locked terminology). The two actions never appear conflated on the same surface, and the circular arrow never appears on an authorization action.

### D7: Remove flow — EB first, best-effort, honest; then full local cleanup

Sequence: confirmation dialog (honest copy: closes the connection; the bank-side consent is closed "where supported" — never promised) → `DELETE /sessions/{id}` at EB → local cleanup in one transaction. Ordering is forced: the persisted session ID is the only handle to the consent (no `GET /sessions` exists), so local deletion before EB deletion permanently loses the ability to revoke. EB failure (network/5xx) **never blocks** removal — the intent principle means the user's explicit choice is not subordinated to a system failure; the result reports honestly: "the authorization remains active at the bank until <valid_until>; your bank's own portal can revoke it sooner." 404 = already gone, proceed. No revocation-retry queue. Local cleanup deletes "everything derived from this connection": `eb_sessions` row, its `accounts`, their `balances`, the session's `sync_log` — one transaction (D5-style deletion hygiene from `add-account-overview`). The phrase "everything derived from this connection" is the spec wording so the transaction and workflow features inherit the obligation.

### D8: Missing-accounts at re-auth — merge defaults to keep; deletion is an explicit follow-up

When re-authorization yields fewer accounts than stored (user deselection, user error, or bank-side identity change — indistinguishable, and IBAN-only matching means a bank-side uid/IBAN change looks identical to deselection), the merge **keeps the missing accounts as local copies by default** — no deletion happens at merge time. The SPA then shows the missing-accounts dialog (renders every time the condition is detected, no remember-preference — rare event, machinery for a non-problem): information ("These accounts are no longer part of the authorization: … They will no longer be synchronized.") + two actions: "Delete newly missing data" (danger — scoped to the newly missing accounts only; already-kept local copies are listed for context but never deleted by this action, per the missing-accounts dialog requirement) / "Keep as local copy" (primary, already the effective state). Server flow stays atomic and crash-safe: if the user closes the tab mid-dialog, the retention-safe outcome (keep) has already happened — the dialog is a post-import notice with a destructive option, not a gate. This abolishes the silent orphan deletion and closes the principle gap where a bank-side identity change would have caused system-initiated data deletion.

### D9: Kept-as-local-copy representation — flag column on `accounts`

`accounts` gains `in_consent INTEGER NOT NULL DEFAULT 1` (name final at implementation). At merge, accounts of the previous same-bank session that do not match the new import are re-pointed to the new session row with `in_consent = 0` instead of being deleted; their `balances` rows survive untouched. The sync runner skips `in_consent = 0` accounts (they are outside the authorization's account filter — PSD2: BankTeller shows exactly what the authorization returns, so they are never re-fetched). Presentation uses the existing freshness vocabulary: permanently stale ("Last updated X ago"), "Local copy" tag, removable via the inline delete affordance (D5) — which deletes the account row + its `balances` in one transaction, gated by a confirmation dialog (the *only* per-account deletion path; the button is the trigger, the dialog is the gate). Alternatives rejected: detaching to a null session (breaks NOT NULL FK, invents a session-less state class); a separate archive table (fragments queries, duplicates schema).

### D10: Automation guard — principle now, enforcement with the workflow feature

User-initiated deletion of account or connection data is blocked while an active automation references it. Blocking surfaces disable the action with a **generic** reference ("used by automations") — the enumerated list + links belong only where the user can act on them (the remove-connection dialog, built by the workflow feature). No degraded automation states, no cascade deletes, no silent breakage: the user modifies or removes the automation first. This change ships the dialog with both actions enabled (no automations exist); the spec records the principle so the workflow feature implements it mechanically. Keeping a local copy is retention, not deletion — an automation referencing a kept account never blocks the *keep* (the guard fires only on later removal).

### D11: Zero-account notice — onboarding first connection only, suggestive

Detection fires only on the onboarding first-connection import (add-mode: no check — the system is already working; re-auth narrowing to zero: covered by D8's dialog). The wizard import step renders a brass Tier-3 DecisionBox notice: reassuring copy (the authorization succeeded and is stored; most banks require explicitly ticking accounts during authorization), footer actions "Continue to dashboard" (quiet left) / "Connect another bank" (loud forward right — re-enters bank selection mid-flow; the just-connected bank correctly appears blocked-connected there). The connection is stored regardless — the onboarding completion condition does NOT change (a bank returning an empty list can be a bank-side glitch; gating on a system state outside our control violates D1). The dashboard empty state remains the standing presentation for the user who continues anyway, with copy refined for the connected-but-zero-accounts condition and a direct "Connect a bank" trigger (umbrella terminology: "Connect", never "Add").

### D12: Absorption — dashboard deltas

The metadata strip's "Add bank" text button is removed; the strip becomes the global sync line + icon-only balance refresh (28dp fixed-footprint icon button). The zero-account/zero-connection empty states keep a direct "Connect a bank" `ActionButton` (first-run call-to-action is not bank management — a brand-new user should not walk Dashboard → Settings → Bank connections to connect their first bank). The empty-state layout covers both conditions (zero connections; connected-but-zero-accounts) with condition-specific copy.

### D13: Connections data — extend `GET /api/accounts`, no new endpoint

The existing `GET /api/accounts` payload already carries per-bank `aspsp_name`, `aspsp_country`, `psu_type`, consent-broken flag, `valid_until`, `last_success_at`, sync status. It gains per-bank `bic` (nullable — stored at authorization time from the staged ASPSP data, mirroring how `logo` is persisted: staged at `POST /api/auth` into the user session from the already-fetched ASPSP list, passed at the callback, persisted by `mergeSession` — the authorize response cannot supply it, Enable Banking's authorize-result ASPSP schema is minimal, the same reason the logo is staged; NULL for existing sessions until their next re-auth, degraded gracefully) and `connected_at` (from the existing `eb_sessions.created_at`), plus per-account `in_consent` so local copies render correctly. One source of truth; the connections view and dashboard consume the same payload. Bank groups are deterministically ordered by ASPSP name, then country (case-insensitive, stable) — the same ordering contract as the wizard's bank listing endpoint (`onboarding` spec, "Deterministic ordering"): a server-side sort so both consumers present identically and the SPA needs no client-side sorting (today's groups follow `selectAllSessions`'s `ORDER BY created_at DESC` — reverse connection order — which neither list should inherit). Accounts within a bank group sort by display name (case-insensitive, NULL names last — `accounts.name` is nullable), then IBAN (names can repeat within a bank; the IBAN makes the order deterministic); both levels sort server-side in the payload, so the Settings card rows and the dashboard cards inherit identical order. Remove is `POST /api/connections/remove` (bank identity payload: `aspsp_name` + `aspsp_country`), authenticated, matching the existing POST-style API conventions; it performs D7's sequence server-side.

### D14: Missing-accounts dialog data flow

The auth callback merge (server-side, atomic) computes the missing set (previous session's accounts not matched in the new import, IBAN-only matching per the schema comment) and reports it via a one-shot informational signal in the user session, set at the auth callback alongside `pendingInitialImport` and carried — and cleared — by the next `GET /api/accounts` response (the callback's own response is the SPA HTML bundle, not JSON, so it cannot carry the set; the signal is informational, not pending-choice state — the keep has already happened); the SPA renders the dialog from that payload. "Delete newly missing data" calls a follow-up endpoint (`POST /api/accounts/delete-local` with the NEWLY MISSING account ids only — already-kept local copies are never in scope for this action, per the missing-accounts dialog requirement; naming final at implementation) that enforces D10's guard (trivially: no automations exist yet) and deletes account rows + balances in one transaction. No pending-choice server state exists anywhere (D8's default-keep makes the flow stateless).

### D15: Dashboard local-copy treatment — archived look, excluded from the hero total

User decision: kept-as-local-copy accounts render greyed (content in `onSurfaceVariant`, the em-dash dimmed convention — never a state tint), tagged "Local copy", with a per-card sublabel ("Local copy — not synchronized"), and are **excluded from the hero total**. Rationale: the hero is the primary trust figure — a frozen balance is an assertion about the past, and as copies age an inclusive total drifts from reality in an unknown direction; the greyed card + tag is the exclusion signal (the same principle as the em-dash: the card carries why it is not included — no asterisk). Local copies never make a bank *contributing* for the hero freshness indicator (permanently stale by design — an indicator would be chronic noise). Contingency edge: when no live account carries displayed balance data but local copies exist (bank offline, all accounts kept), the hero shows the placeholder with a quiet note line ("N accounts are kept as local copies — reconnect a bank to restore the live view") — the retention principle (data survives visibly) without asserting stale figures as current. Consistency: the dashboard agrees with the connections section's permanently-stale presentation instead of split-braining the same data.

### D16: Cross-session account matching — identification_hash first, IBAN fallback

The Mock ASPSP sandbox finding: IBAN-less banks expose accounts that the IBAN-only merge can never match, so **every re-authorization of such a bank reports all accounts as missing and duplicates them** — even on an identical selection — firing a false-positive missing-accounts dialog (a system-caused false positive driving the user's delete decision, contrary to D1's spirit) and making the accepted null-IBAN duplication risk the *default* behavior for whole banks. Fix: Enable Banking provides the exact key for this — `identification_hash`, a **required** field on every account in the authorize response, documented as usable "for matching accounts between multiple sessions (even in case the sessions are authorized by different PSUs)", derived from whatever identification the account carries (IBAN *or* the non-IBAN tuple — the spec's own example hashes `[aspsp_country, account_id, other, scheme_name]`). This is the field VISION.md §5.1 always intended ("Match accounts across sessions using `identification_hash`"). The archived `2026-08-24-onboarding-account-linking` design codified the IBAN deviation on the premise that IBAN "serves the same purpose once stored" — equal capability assumed, IBAN-less duplication accepted as a residual limitation; the sandbox finding disproves the premise for IBAN-less banks, and this change's D8/D9 keep-semantics escalated the cost of the limitation (false-positive dialogs + duplicate rows per re-auth instead of quiet cruft). The cascade: match by hash first (both sides carrying one), fall back to IBAN (pre-migration rows with NULL hashes; the prior behavior with its global-uniqueness property intact). Side effects: a true IBAN change with a stable hash now updates the row instead of duplicating (improving the original bank-side-identity-change case D8 was written for), and the merge's missing-set computation is only reached with a genuinely unmatched account. `identification_hash` is persisted on `accounts` (nullable — NULL only for pre-migration rows and malformed responses), captured at authorization time alongside the account's other fields; the D11 "detect accounts added at the bank without re-auth" door (GET /sessions `SessionAccount` also carries the hash) now has its key already stored.

### D17: Import-step confinement — navigation stays live (user ruling + designer sign-off)

The wizard's initial-import step (in-flight, failed, and the zero-account notice) renders confined inside the dashboard's content zone with the tab bar visible and the greeting above it — never a full-page takeover. Rationale: the import run is server-side and disconnect-safe (a backgroundable process — D12 of `add-account-overview`), so suppressing navigation served no functional purpose; the user may edit settings or connect another bank mid-import. Designer sign-off (post-connection-fix): four CONFIRMs on the core, two AMENDs applied — (1) the greeting renders above the confined step (without it, the zone reads as a detached blank canvas rather than the user's dashboard); (2) the failure action relabels "Continue anyway" → "Continue to dashboard" (names the destination now that the shell is present; aligned with the notice footer). Also confirmed: the plain centered wait composition (framing an ambient wait in a card/DecisionBox is a tier-escalation error), failure-state persistence (a tab switch never auto-transitions into the degraded presentation — navigation is side-effect-free), and notice persistence (no auto-continue on tab-away; a Tier 3 decision requires an explicit choice).

### D18: Ever-onboarded marker — remove-all never regresses to the wizard

The implementation review's significant finding (F1): removing the last bank connection makes `auth_completed` ("has any session") flip false, so a reload routes to bank selection instead of the dashboard's empty state — a spec self-contradiction between 12.4's "reload → state consistent everywhere" and the resolver's session rung, plus a dead-letter-stage resurrection hazard (a stale `auth_progress`/`bank_selection` stage becomes consumable again, breaking the client-side add-mode premise — D15 of `add-account-overview`). Ruling (user decision, option 1 of the review's two): a persisted **ever-onboarded marker** (a `system_config` key, set at first authorization in the merge transaction, cleared only by the re-registration purge) keys the resolver's dashboard rung. The user's failsafe framing is served by rungs 1–3 (missing credentials / deleted / inactive application → registration/activation regardless of connections) — the repair paths are untouched; the marker rung only decides where a HEALTHY ever-onboarded user with zero connections lands, and the answer is the dashboard's standing empty state with its "Connect a bank" action (a deliberate, confirmed removal is not a regression; the empty state reaches the identical wizard in one click; Settings and the remove caveat stay reachable — the wizard would lock the user out of the screen that explains what happened). Rejected alternative (accepted deviation): zero code, but keeps the dead-letter resurrection and requires purging stages on removal anyway — not actually cheaper. The onboarding completion condition is UNCHANGED (first authorization completes onboarding, exactly as the non-goal states); only the resolver's routing key changes. Pre-change users derive as onboarded on read (no mis-routing on upgrade).

### D19: CropSignaledScroll — the wrapper generalization, with the shell-covered exemption

The bank-list geometry defect (the wizard scaffold's zone-edge hairline rendered over the pinned search field — the placement assumed the whole zone was the scrollable) exposed that the crop-signal concept needed a mechanism, not per-surface overlay code. Ruling: a reusable `CropSignaledScroll` wrapper renders the hairlines at ITS OWN bounds (top while scrolled past offset 0, bottom while canScrollForward, dissolving at the ends, never at rest), parameterized over `ScrollState`/`LazyListState`, mirroring the existing `derivedStateOf` predicates. **Scope — the wrapper serves in-surface scrollables the shell does not already signal**: the wizard steps (the scaffold is its own chrome; the zone-edge overlays are retired), bounded dialog lists (the missing-accounts dialog), and future ad-hoc scrollables. **Exemption (the reviewer's geometric finding)**: surfaces whose crop edges the shell already signals from the same scroll state get NO wrapper — the Settings master-detail panels (the panel's top edge IS the top bar's boundary; the wrapper would render coincident, same-tone, same-trigger hairlines — pure redundancy) and the shell-scrolled surfaces (dashboard, legal pages — they scroll the shell's own zone; wrapping creates a nested scrollable and would orphan the shell's LedgerScrollbar). The one-line rule generalizes as: every scrollable shows crop signals where the crop happens — via the wrapper where the shell doesn't already provide them, never twice at the same edge. **Ownership split**: the scrollbar stays in `LedgerScrollbar`, the hairlines move to the wrapper — the two overlays compose (either nesting order works; the wrapper hosts the scrollbar's scroll state, the scrollbar overlays the same bounds; the migration sites state the order: the wrapper's Box hosts the scrollable, the LedgerScrollbar wraps the same state inside the wrapper's content slot, so the scrollbar's trailing-edge inset measures against the wrapper's bounds). Alternatives rejected: the wrapper owning both (couples the two affordances' lifecycles — the scrollbar has its own fade/touch behavior and its own requirement); per-surface overlays forever (the defect this ruling fixes).

### D20: The 2dp detachment gap — crop signals never touch the content they crop

The user's finding: the crop hairline is identical in weight and tone to the card/info-box outlines (deliberately — one hairline vocabulary), so when content crops beneath chrome, the hairline reads as the panel's own top border; the only differentiator was sharp-vs-rounded corners. The designer's diagnosis: Gestalt closure — a cropped card's side borders terminate against a flush hairline at 90°, and the eye binds the segments into one closed rectangle. The ruling: a **2dp empty band between the hairline and the content's clip plane** — purely spatial, the hairline tone unchanged (a louder line without the gap reads as a highlighted border and elevates machinery over figures). 2dp not 1dp (fractional zoom at 125%/150% and the light theme's subtle background/fill luminance delta collapse a 1px sliver), not 4dp (an exaggerated void). **Mechanism split per surface**: the SHELL hairlines (top-bar divider, bottom-bar crop hairline) are OVERLAY OFFSETS — the clip plane stays at the zone boundary, only the hairline is displaced 2dp into the chrome zone; at rest nothing stays (no content padding — a permanent shell inset would break the at-rest seam and shift all content). The WRAPPER (`CropSignaledScroll`) is a permanent content-slot inset — at rest the 2dp inset stays as breathing room (fixed, no layout shift when the hairline fades in). Uniform across all four hairline surfaces; the Settings master-detail's vertical divider is exempt (a permanent structural separator, not a crop signal). Transience alone was insufficient: reading is contemplative, and during any scroll pause the signal is static — the static representation must be self-explanatory.

## Risks / Trade-offs

- [`NavigationSuiteScaffold` alpha at CMP 1.11.1] → hand-rolled tab bar (D3) and settings layout (D4); only `material3-window-size-class` added (stable on wasmJs). Verified on Maven Central during exploration.
- [Post-DELETE `GET /sessions/{id}` behavior undocumented (404 vs `CLOSED`/`REVOKED`); DELETE idempotency undocumented] → defensive handling (404 = already gone); the provisioned sandbox integration test can settle both empirically during implementation.
- [Kept-as-local-copy accounts could accumulate silently] → they are visible by design: "Local copy" tag in the connections list, permanently-stale presentation, inline remove affordance; the missing-accounts dialog appears every time the condition is detected.
- [Merge default-keep supersedes the prior orphan-deletion behavior and its accepted risk] → deliberate (D1/D8); the prior accepted risk ("sync run in flight while merge deletes old session → orphaned balances rows") shrinks correspondingly — kept accounts' balances are intentionally retained, not orphans.
- [Two-pane Settings vs `ScreenShell` divider discipline] → the top-bar divider keys on the active panel's scroll offset (D4); at rest the sheet stays borderless.
- [Connection cards with many accounts explode vertically] → 4-row cap + expander (D5).
- [BIC NULL for existing sessions until next re-auth] → degrades gracefully (hidden when NULL), same convention as `logo`/`valid_until`; no backfill machinery.
- [Wizard re-entry from the import step ("Connect another bank") is new wiring] → the add-mode machinery (client-side, D15 of `add-account-overview`) exists; only the import-step → bank-selection re-entry path is new.
- ["Refresh" terminology collision between balance sync and authorization renewal] → icon-only balance refresh vs. text+lock authorization refresh (D6); locked terminology ("refresh authorization" ≠ "balance refresh") enforced in copy.
- [Remove during in-flight sync: the runner snapshots sessions up front and SQLite FK enforcement is off, so mid-run writes against removed rows would create invisible orphans] → existence re-check before each balance upsert and the sync-log write (specced in the `balance-sync` delta); a guarded no-op never fails the run.
- [Null-IBAN accounts under keep-semantics: a null-IBAN account never IBAN-matches, so a re-auth of a bank reporting IBAN-less accounts now duplicates rows (kept copy + new live row) where deletion previously removed the orphan] → RESOLVED by D16 for hash-carrying accounts: the identification-hash match succeeds for IBAN-less accounts, so an identical re-selection matches every row (no false-positive dialog, no duplication); the residual (an account with neither a matchable hash nor IBAN — malformed responses only) remains accepted and rare.
- [Crash window between the EB delete and the local cleanup transaction] → self-heals: the local session survives while its EB session is gone, so the next sync's `getSession` records `SESSION_DOES_NOT_EXIST` → consent-dead presentation; the user re-removes or re-authorizes. The remove endpoint also answers an honest not-found for a bank with no local session row (stale SPA state / double-remove) — no EB call, no deletion.
- [Hash rotation at EB/ASPSP (D16's "stable across sessions" documentation claim proving false)] → IBAN-carrying accounts degrade gracefully to the IBAN fallback; IBAN-less accounts regress to the pre-D16 behavior (duplicates + false-positive dialog) — the status quo, but the user-facing symptom returns silently. The D16 regression walkthrough (tasks.md group 12, the missing-accounts walkthrough) verifies the premise against the real Mock ASPSP; the self-healing fallback (a matched row persists the incoming hash) softens the transition.
- [Pre-migration null-IBAN residual (D16): an account authorized before this change with NULL hash AND NULL IBAN can match by neither key] → its first post-upgrade re-auth reports it missing (kept as a local copy) and inserts a fresh row — a one-time false-positive dialog + duplicate per such account. Retention-safe, self-resolving after one cycle (the fresh row carries a hash); explicitly accepted. ## Migration Plan

1. SQLDelight migration: `eb_sessions` gains nullable `bic`; `accounts` gains `in_consent INTEGER NOT NULL DEFAULT 1` (existing rows are synced accounts — correct default). ALTER TABLE, existing rows untouched.
2. `DatabaseFactory` version-inference ladder (`user_version = 0` path): extend the existing pattern — the new schema is distinguished by the new columns; prior states resolve and migrate, never "assume latest". Covered by a JVM test on the partial path, mirroring the established convention.
3. Merge logic change (D8/D9) deploys with the migration: existing behavior (orphan deletion) is replaced by default-keep; no data transformation needed (nothing to backfill — deletion simply stops happening).
4. Deploy: migration applies on startup; the new Settings surface and tab bar are additive; the dashboard's "Add bank" control is replaced by the empty-state trigger and the Settings section.
5. Rollback: reverting the image leaves the new columns orphaned but harmless (nullable / defaulted; no existing query touches them). Kept local copies created under the new logic remain ordinary account rows under the old logic's merge (they would be deleted at the next re-auth — acceptable within a rollback scenario).
